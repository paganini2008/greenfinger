One url in. A searchable archive out.

Greenfinger is a distributed web crawler for the JVM. Point it at a url and it crawls the whole site, keeps every page, every picture and every version, and writes plain files, a full text index and a vector collection in one pass. Every node runs the same jar, so there is no coordinator to deploy and nothing to provision before the first crawl.

Get started GitHub Documentation

Greenfinger = a crawler that never leaves the site + three outputs that stack + search by words, by meaning, or by describing a picture.

A rebuild in progress. v1 keeps answering searches while v2 is being written, and each node reports what it pulled.

Why

Most crawler code starts as a hundred lines around an http client and works. These are the five things that arrive next.

The crawl wanders off

One advert link, one external share button, and an unbounded crawler is downloading the rest of the internet.

Two boundary rules that cannot be switched off.

One machine is not enough

Doubling the speed means a queue, a scheduler, a lock, and a week of work that has nothing to do with the site you wanted.

Every node runs the same jar and pulls its own share.

It restarts from zero

The process was killed at page 40,000 and the queue was in memory.

The frontier is on disk, so a resume carries on.

The text is mostly furniture

Navigation, sidebars and cookie banners get indexed alongside the article, so every result looks the same.

Boilerplate dropped by link density, in any language.

Storing it is a second project

Files here, an index there, embeddings somewhere else, and three pieces of glue that each fail differently.

One pass writes all three, and any of them rebuilds from the files.

Everything a crawl needs, nothing to provision

No database, no search server, no API key and no model download before the first crawl. H2 and an embedded Lucene index are the defaults, and the embedding models run as ONNX inside the crawler's own process.

◈

Decentralised by default

One url dispatched is one call to whichever node owns it. No central queue, no scheduler, no leader in the fetch path.

⇲

Scales by starting a process

Point another one at the same cluster name and it joins a crawl that is already running. Kill one and the crawl carries on.

⛁

Three outputs, and they stack

Files on disk or in MinIO, an index in Lucene or Elasticsearch, vectors in Lucene, Qdrant, Weaviate or Elasticsearch.

⟳

Replay without recrawling

The index and the vectors rebuild from the files. A lost index or a changed analyzer never means touching the site again.

⊘

Never leaves the site

The registrable domain has to match and every url has to sit under the start url. Neither rule can be switched off. robots.txt on top.

▤

Beyond html

Pictures from <img>, srcset and og:image. Document links recorded on every crawl, with pdf one bean away.

↺

Resumable and versioned

A crawl killed halfway carries on. A rebuild opens a new version beside the old one, which keeps answering searches until it finishes.

✦

Search three ways

By words, by meaning, and by describing a picture you remember. The embedding models run locally and need no account.

⚙

Every decision is a seam

Fifteen interfaces, each with a shipped default that is @ConditionalOnMissingBean. Publish a bean and yours wins.

How it works

One crawl writes three places at once. The file layer is always on, because the database keeps metadata only and the other two rebuild from what it wrote. That is the whole reason replay can exist, and it is why search never has to read the database. 

// one pass, three outputs

                  ┌─────────────┐
                  │  file       │  disk, MinIO, S3
 one crawl  ────► ├─────────────┤
                  │  index      │  Lucene, ES
                  ├─────────────┤
                  │  vector     │  Lucene, Qdrant,
                  │             │  Weaviate, ES
                  └─────────────┘
                        │
       replay ──────────┘  rebuild from the files,
                           without fetching again
// the cluster, fork without join

 node A ── finds /a/b ──► node C owns it
                             │
                     fetches, finds /a/b/c
                             │
                      ──► node A owns it ──► ...

 no central queue
 no leader in the fetch path
 join or leave mid crawl

A crawl is a recursive function, and distribution only makes the recursive call cross a process. There is no join, because a parent page does not care what its children found. Finishing is decided from shared counters that every node can read, so a leader that dies mid crawl cannot leave a crawl that never ends.

From clone to a searchable site in one command

The crawler needs nothing else running. Metadata goes into an H2 file, pages go under ./data, and a live dashboard is drawn while it works. First crawl in about five minutes, most of which is Maven.

Browse the repo 

# clone and build
git clone https://github.com/paganini2008/greenfinger
cd greenfinger/backend && mvn clean install

# crawl a site, right now
cd ../deploy
./greenfinger-cli.sh --cluster=demo crawl \
    --url=https://books.toscrape.com

# or bring up the nodes and the console
./run-local.sh              # http://localhost:9700
GF_NODES=3 ./run-local.sh   # three nodes, one crawl

# a terminal on those nodes
./greenfinger-shell.sh --cluster=greenfinger-local

Performance

Our own numbers only. There is no comparison here against other crawlers, because we have not run the controlled experiment that would make one honest.

Test environment. Apple M2 Max, 12 cores, 32 GB, macOS 26.3.1, JDK 17.0.12. Two nodes started by run-local.sh, each -Xms256m -Xmx2g. H2 file, embedded Lucene index, embedded Lucene vector store, pages and images on local disk, local ONNX embeddings. Home broadband. Polite crawling, so fetchInterval is the floor on throughput rather than the hardware.

Pages kept against urls seen

books.toscrape.com, 1 node 1,000 pages / 4m 12s
simplefood.blog, 2 nodes 140 pages / 5m 01s
apod.nasa.gov, 2 nodes 46 pages / 1m 41s

The gap between urls seen and pages kept is the point rather than an inefficiency. On simplefood 22,340 urls were filtered out by the boundary rules and 561 were duplicate content, which is work the outputs never had to do.

How evenly two nodes shared one crawl

On three nodes against a 61 page site with one shared PostgreSQL: 61 dispatched, 61 saved, each page fetched exactly once.
