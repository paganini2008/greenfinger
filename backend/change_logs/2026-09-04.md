2026-09-04 backend
========================================

Completion, and who decides it
========================================

The day was one refactor and its consequences. `2026-09-03` closed with two defects on the list --
a crawl that never ends, and a `rebuild` that never publishes -- and they turned out to be the same
mistake seen twice: the decision that a crawl is over had been moved out of the shared state and
into the leader.


## What 1.x did, and why it was right
------------------------------

1.x had no leader. `DefaultWebCrawlerExecutionContext` registered itself with a
`SerializableTaskTimer(5, 5, SECONDS)`; every five seconds, **on every node**, the timer called
`shouldInterrupt()`, which asked two checkers -- `maxFetchSize` and `fetchDuration` -- about the
dashboard and set `completed` if either fired. The dashboard was Redis, so the flag was shared and
whichever node noticed first was simply the one that wrote it.

That is not a weaker design than a leader deciding. It is a stronger one: every node can answer, so
no single node's absence stops the answer being reached, and the shared flag makes it idempotent
without anybody arranging that.

2.0 had kept the two checkers but moved the third question -- has everything dispatched been
handled -- into `CrawlCluster.supervise()`, leader-only, iterating `coordinators.keySet()`. That
sentence contains both bugs.


## Bug 1: a leader outside the crawl never declares it finished
------------------------------

`coordinators` is filled by `create()`, which only runs when *this* node joins a crawl. So the real
semantics were "the leader supervises the crawls it happens to be taking part in". Three ways to
fall out of that, two of them in yesterday's logs:

- join threw -- `node-2.log`, `node-3.log`: "Could not join the crawl ... No catalog with id"
- join was refused by the semaphore -- `node-2.log:69`: another catalog was running here
- **leadership changed** and the new leader was not in the crawl. Unavoidable, and it happens
  exactly when it matters.

The engine then sat in `ThreadUtils.sleep` waiting for `isCrawlFinished()`, and the stale timeout
did not save it because that check was inside the same leader-only branch.


## Bug 2: `endedItself` lost a race with the shared flag
------------------------------

`CrawlerEngine`'s loop began `if (context.shouldInterrupt()) break;` -- which read the **shared**
completed flag -- and its `finally` ended `stateManager.setCompleted(true)`. So the first node to
leave flipped the flag, every other node broke out through that first line with `endedItself =
false` and a blank reason, and `selfTerminated` came back false. `CrawlerLauncher` publishes on
`completed && publisher`; the leader only had to not be first out to publish nothing. That is
`rebuild` leaving `search=v0` with `index=v1`.


## Bug 3, found while reading: the shared dashboard was never reset
------------------------------

Not on any list, and worse than either of the above.

1.x reset the whole dashboard at the start of a run -- `RedisDashboard.afterPropertiesSet()` set
`completed=false` and every counter to zero -- and only on the initiating node, guarded by
`RedisGlobalStateManager`'s `initialized` flag, because a node joining a crawl in progress must not
zero the numbers it is about to add to.

2.0's `ClusterDashboard.afterPropertiesSet()` only did `setIfAbsent` on startTime and endTime. The
counters and the completion flag were never cleared, and the only cleanup was a 24 hour TTL. So a
second `crawl` or `update` of the same catalog at the same version, within a day, read back
`completed=1` and **ended before it began**. `rebuild` escaped because the version increments;
single-node escaped because its dashboard is in memory. Which is why nobody had seen it.


## What it is now
------------------------------

**Two checkers, and they are the whole definition of a finished crawl.**
`InterruptionChecker` -> `CompletionChecker` (`core.component.interrupt` -> `.completion`), with
`shouldInterrupt` -> `isCompleted`. `maxFetchSize` is asked on the crawl's own thread, because the
counter it watches only moves when a page goes past; `fetchDuration` is asked by a clock, because
time passes whether or not anything is being fetched -- and a run whose threads are all blocked on
a site that stopped answering is precisely what that limit is for.

**The clock lives in the context**, one thread per run, five seconds apart
(`greenfinger.completion-check-interval`), which is what 1.x's task timer was.

**Publishing is `isCompleted()` and nothing else.** No local inference. `endedItself` is gone,
`CrawlCoordinator.isCrawlFinished()` and `finishedReason()` are gone, `CrawlCluster.supervise()` is
gone, and the control channel's `STOP` and `FINISHED` messages are gone with them -- they only
existed to carry a conclusion back from the leader, and the conclusion is shared state now.
`ControlMessage` is down to `STARTED` and `RESTORE_FILES`.

**The reason is shared too.** `setCompleted(completed, reason, interrupted)`, first writer wins, so
a crawl that hit `maxFetchSize` and was then wound down reports the limit rather than the wind-down
-- and all three nodes report the same sentence instead of each guessing from what it saw.

**The watchdog tells two kinds of quiet apart.** `isTimeout` was dead code carried over from 1.x
(declared, implemented twice, called nowhere) and its cluster implementation read a *local*
`lastModified`, so a node waiting for work would have called a busy crawl stalled. It now watches
the shared counters and remembers when they last changed. When they have not moved for
`greenfinger.idle-timeout`:

| | means | result |
|---|---|---|
| `dispatched == handled` | nothing queued or in flight anywhere; the site ran out of urls | **completion**, published, without waiting out `fetchDuration` |
| `dispatched > handled` | a node stopped answering holding urls | **intervention**, nothing published, the frontier keeps what was missed |
| `dispatched == 0` | the entry point never went anywhere | **intervention** |

`dispatched == handled` is not a third checker: it does not decide completion, it only says which
kind of silence this is.

**What this costs.** A site smaller than `maxFetchSize` now sits there for `idle-timeout` after its
last page, because nothing else ends it -- the engine no longer breaks out when its own frontier
drains, and it should not: an empty frontier on one node says nothing about the other three. Both
timeouts are `Duration`s rather than numbers so they can be tuned in either direction, and the idle
default is **two minutes** rather than 1.x's five. The tests set 600ms, since their sites are three
pages on localhost.

**Reset is back.** The initiating node clears the shared counters, flag and reason in
`afterPropertiesSet`; a joining node does not. `WebCrawlerComponentFactory.getGlobalStateManager`
takes the `initiator` flag for that reason and nothing else. Deleted rather than blanked -- the
reason is written with `setIfAbsent`, so a blank left lying there would count as "already written".

**The leader now does exactly one thing: publish.** And that is not a correctness mechanism either
-- publishing twice writes the same row twice, pruning what is pruned removes nothing. Asking one
node is about not doing the same work three times.


## Sign-in tokens are signed, not stored
------------------------------

Yesterday's open decision, settled: stateless.

A token now carries who it is for, what they may do and when it stops working, signed with
`GF_TOKEN_SECRET` (HMAC-SHA256). Any node with the same secret verifies one it never issued, which
is what makes putting nginx or kong in front of several nodes possible at all. Unset, each process
generates its own and logs a warning: one node still works, tokens do not survive a restart and
peers do not accept them.

`run-docker.sh` says so when started with more than one node and no secret, and the front end
container went from failover back to spreading requests across every node -- which is what the
per-node token map had made impossible.

Signing out is the one thing a signed token cannot do by itself, so it is recorded in a small local
set until the token would have expired anyway. Honoured on this node, not on a peer. The answer to
that is short-lived tokens, not a shared blacklist -- which would put the state back where it was.


## The front end container runs Node, and its port is 9700
------------------------------

nginx is gone from `deploy/`. `web/server.js` is about a hundred and fifty lines of Node's own
`http` module -- static files, the single page app fallback, and `/v2` and `/actuator` forwarded
round robin over `GF_UPSTREAMS` -- with no dependencies at all. A `package.json` for that would
mean an npm install in the image, a lockfile to keep current, and a supply chain for a hundred
lines of code. `Dockerfile.web` is `node:22-alpine` and runs as `node` rather than root.

Two things made it worth changing rather than keeping the config file: the api address became a
runtime setting the container writes (`env.js`), and the forwarding rules are three lines of code.

The port is **9700** now, in both the container and the Angular dev server, so "the front end is on
9700" is true either way. `GF_CORS_ORIGINS` follows.


## Bloom filter dedup, added and then taken out again
------------------------------

Written, tested, and removed the same day at your request: the crawler keeps one url filter, the
RocksDB one, which is exact and durable.

It is worth saying why, because the code was fine and the trade was not. A bloom filter answers
"seen" with a probability rather than a fact, so roughly one page in a hundred is skipped although
it was never crawled -- silently, with nothing anywhere to say which pages. That is a reasonable
price for a crawl of a hundred million urls and a bad one for a catalog anybody has to trust, and
this is a tool for building catalogues people search.

**The extension point stays.** `ExistingUrlPathFilter` is still an interface, a catalog still names
its filter, and `WebCrawlerComponentFactory` is still `@ConditionalOnMissingBean` -- so an
application that wants a different kind of dedup supplies its own factory and answers to whatever
name it likes. The prompt no longer checks the name against a list for exactly that reason: an
unknown one is refused by the factory that was asked for it, when the crawl starts, which is the
only thing that knows what names are valid.

## The rest of 1.x that was missing
------------------------------

Yesterday's audit of 108 1.x classes left five gaps. Where they stand:

- **Login-mode crawling** (`StatefulExtractor` and its four implementations,
  `ExtractorCredentialHandler`, the `CatalogCredential` table, `catalog.credentialHandler`) --
  **not being done**, decided today.
- **Progress bars** -- done, both ends. 1.x drew two, one per limit, and that is the point: a crawl
  ends on whichever arrives first, and a single bar at 60% cannot say whether that is 60% of the
  pages or 60% of the time. The prompt now draws `size` and `time` separately, with an ETA from the
  average page time; `CatalogSummary` carries `sizeProgress` and `timeProgress` for the front end,
  with `progress` left as the nearer of the two so nothing that read it breaks.
- **`upgradeCatalogIndex`** -- **not being done**: `replay --layers=index` already rebuilds the
  index from the database rows without touching the version, which is the same operation.
- **Bloom dedup** -- written and removed, above. rocksdb is the one filter that ships.
- **Startup configuration dump** -- done. `ConfigurationReport` prints every greenfinger
  `@ConfigurationProperties` bean after the context is up, which is the only honest answer to
  "which of the four config sources won".

`loadRunningCatalogDetails` had no callers; it does now. `catalog-show` without an `--id` shows
whatever is crawling, and everything it prints comes from `CatalogDetails` rather than the
`Catalog` row -- the row is how a catalog is stored, details is what it means once defaults are
applied, and printing the row reported a blank wherever a default was in force. Its "Last run"
section is gone; `crawler-report` does that properly, from the report rows, and two answers to one
question is one too many.


## Settings left the command line
------------------------------

Five launchers had five ways of being told the same things. `deploy/run.conf` is now the one file
all of them read -- `greenfinger-cli.sh`, `greenfinger-face.sh`, `greenfinger-api.sh`,
`run-local.sh`, `run-docker.sh` -- and `--data-store`, `--cluster`, `--cluster-hosts`,
`--worker-dir`, `-n`, `-p`, `-d`, `-H`, `--no-web` and `--web-port` are gone with it. Typing one
gets a message naming the setting that replaced it rather than "unknown argument".

The line keeps what varies per command: `--id`, `--node`, `--layers`, `--json`. What does not vary
per command is not an option -- it describes the installation, and a run that has to be reproduced
tomorrow is the normal case here. `run-local.sh` and `run-docker.sh` are down to verbs (`start`,
`stop`, `status`, `logs 2`, `build`, `help`), and `greenfinger-face.sh` takes nothing at all:
return and you are at the prompt.

Anything already exported still wins, so `GF_NODES=3 ./run-local.sh` needs no editing. `.env` keeps
what must not be committed and nothing else; the front end's port moved out of it into run.conf.

**Two things this broke, both fixed.**

`mvn package` copies `src/main/resources/bin` over `deploy/` with `overwrite=true`, which would
have replaced an installation's settings on every build. run.conf is copied by a second execution
with `overwrite=false`: a build gives it to an installation that has none and never touches one
that has been filled in.

An empty value in a settings file has to mean "not set". Spring reads `${GF_CLUSTER_PORT:22000}` as
"22000 unless the variable exists", and `set -a` turns an empty line in run.conf into a variable
that exists and is empty -- so the default never applied and the bind failed on an empty int, with
the shell refusing to start at all. Every launcher now drops the empty `GF_*` after sourcing, which
is what lets run.conf ship a key with no value beside its explanation.

**One log directory** (`GF_LOG_DIR`, default `logs/` beside the launcher). Four scripts each
choosing their own is four places to look when something went wrong overnight; the file name
already says which process wrote it -- `greenfinger.log`, `greenfinger-api.log`, `node-N.log`,
`cli-worker-N.log`. Forked workers used to log inside their own data directory; `LocalNodes` now
writes to the shared one too.


## The command line and the prompt, told apart
------------------------------

Same commands, both ways -- checked: every one of the twenty `@Command` names is reachable from the
one-shot dispatcher, which also takes seven short aliases the prompt does not. What differs is how
long the process lives, and two commands had not been told:

**`status` is a snapshot from the command line.** A session outlives the crawl it started, so
watching makes sense there: the block redraws until the crawl ends or you type q. A one-shot
process exists to answer one question and exit, and watching would mean holding a terminal open on
a crawl belonging to a different process. It now prints one frame -- the same view the prompt
animates, counters flushed first so it reports this instant rather than the one before -- and
returns.

**`catalog-save` takes `--json`.** Twenty settings is a good interview and a terrible command line;
as flags it is a line nobody types twice, with the failure mode that gives command lines a bad name
-- mistype one and the crawl starts anyway on a default nobody chose. From the command line it used
to just refuse: "needs a terminal". Now the whole catalog is one argument, in exactly the body
`POST /v2/catalog` takes, so a script written against the server works here.

It is a patch, not a replacement: with `--id` only the keys present are changed, without one the
keys left out take their defaults -- which is what pressing return does in the interview.


## deploy/ is made, not written
------------------------------

Nothing in `deploy/` is in the repository any more -- `.gitignore` has one line, `/deploy/`. It was
half committed and half generated, with four files existing twice: `mvn package` copies
`src/main/resources/bin` and `config` over it, so the copy somebody edited lost every time anybody
built. Two sources of truth for one file, resolved the only way that stays resolved.

Where each piece is edited now:

| In deploy/ | Source |
|---|---|
| `greenfinger-cli.sh`, `greenfinger-face.sh`, `run.conf`, `.env.example` | `backend/greenfinger-shell/src/main/resources/bin/` |
| `run-local.sh`, `run-docker.sh` | `backend/greenfinger-api/src/main/resources/bin/` -- they start the server, which is what that module is |
| `config/` | `backend/greenfinger-shell/src/main/resources/config/` |
| `docker/Dockerfile`, `dockerignore` | `backend/greenfinger-api/src/main/resources/docker/` |
| `docker/Dockerfile.web`, `docker/server.js`, `docker/static/` | `frontend/greenfinger-ui/`, by `npm run build:deploy` |
| `lib/` | the two executable jars; `bin/` was the old name |

The directory is now only: the four launchers, `run.conf`, `.env`, and `config/ lib/ docker/ data/
logs/`. `bin/`, `.run/`, `workers/`, `static/`, `web/`, `test-results/` and two Dockerfiles at the
top level are gone -- pid files went into `logs/` beside the logs of the same processes, and forked
workers into `data/workers`, beside `system/` and `user/` rather than inside either.

Deleting `deploy/` and rebuilding is safe, with three exceptions a build cannot put back: `data/`,
`.env`, and a `run.conf` that has been filled in -- packaging writes that one only when it is
missing.

**One real bug came out of the move.** `.dockerignore` went into `docker/` with the Dockerfiles,
where docker never reads it: it is read only at the root of the build context, and the context is
`deploy/`. Every `docker build` would have uploaded the whole data store and log directory first.
It ships as `dockerignore` (the resources plugin skips a leading dot) and `run-docker.sh` puts it
where docker looks before building.


## An emptied catalog is back at v0
------------------------------

`CatalogStore.resetVersions` is new, and `DeletionService` calls it once every version has gone --
`cleanCatalog` and `deleteCatalog`, never the version-by-version delete, because removing three of
five versions leaves the other two where they are and renumbering them would break every report
that names one.

Without it the next crawl wrote v3 into a catalog whose v0 to v2 exist nowhere: a first crawl
reporting itself as the fourth, and a `search_version` pointing at something that had been deleted.
`index_version` goes to 0, `search_version` to -1, `lastIndexed` to null -- which is exactly what a
catalog that has been defined and never crawled looks like.

The replicated store announces it, because the version numbers are what every node's searches and
crawls are addressed by: a node that missed the reset would go on serving a version that no longer
exists anywhere.

**Not supported:** emptying or deleting several catalogs at once. One catalog, any number of its
versions -- `--version`, `--keep-latest`, `--all` -- which is what the front end's panel offers too.


## Elasticsearch answers the semantic search too
------------------------------

`ElasticsearchVectorStore`: `dense_vector` and `knn`, over the same Lucene HNSW the embedded store
uses. A deployment that already runs Elasticsearch for the index was one service away from running
a vector database as well -- to install, watch, back up and upgrade, for one field per document.
Now `prod` is three servers rather than four: PostgreSQL, MinIO, Elasticsearch. Qdrant and Weaviate
stay, chosen with `GF_VECTOR_STORE`, for a deployment that has one.

Addressed exactly as the other three are: a collection is an index named for the embedding width
(`greenfinger_text_384`), so two models never share a space; catalog and version are keyword fields
filtered at query time. Only what is filtered is mapped -- the payload is `enabled: false`, because
it exists to be handed back with a hit and indexing it would double the index for nothing.

Two details that are not obvious and are the difference between working and looking like it works:

- **The candidate pool is wider than k.** Elasticsearch filters *after* walking the graph, so a
  walk of exactly k rows filtered to one catalog returns fewer than asked -- which reads as missing
  data, not as a narrow search. `num_candidates` is 4k with a floor.
- **Deletes refresh.** The count somebody reads immediately afterwards is how they decide whether
  it worked, and an unrefreshed index answers with what was true a second ago.

**A real bug found while writing it: Qdrant's api key went in the wrong header.** It was put in
`Authorization`, and Qdrant reads a header of its own, `api-key` -- so a Qdrant with authentication
turned on would have answered 401 to a perfectly well formed request. Weaviate's
`Authorization: Bearer` was right. It had never shown because the Qdrant here has no authentication.
`RestJsonClient` now takes the header name.


## The regression found twelve bugs, and one of them was the crawler
------------------------------

The end to end run -- start a node, create a catalog through the api, crawl it the way the front
end does, search it, empty it -- had never once completed. Making it complete is what this section
is. Each of these was a real defect, in order of how much it mattered.

**A site on its own port was crawled one page deep and no further.** A catalog created without a
path pattern is given one, built from its own url: `**.localhost`. The port was not in it, and
AntPathMatcher compares the host segment literally, so the pattern a catalog was born with matched
none of the catalog's own links. Every link found on the entry page was rejected, the crawl ended
with one page saved, and nothing anywhere said why -- the rejections are counted, not logged.
Every site not served on 80 or 443 was affected, which is every site anyone develops against.
`defaultPathPattern` now keeps the port, and the test asserts the pattern matches its own pages
rather than asserting the string, which is what the old test did and why it passed.

**A finished crawl reported no reason for finishing.** `ReadonlyDashboard` is the snapshot the
registry keeps after a crawl leaves it, and it copies eighteen fields. Two of them -- the
completion reason and whether the run was interrupted -- were added by the completion work and not
added here, so they fell through to the interface defaults: null and false. The Monitor page reads
that snapshot for every crawl that is not currently running, which is all of them a second after
they end.

**The published version never caught up.** A crawl carries the catalog it started with, and asks
it for the version numbers. That copy says search is serving nothing -- true when the crawl began,
false the moment it published. A page polling until `searchVersion` reaches `version` polls for
ever. The summary now takes its counters from the run and its versions from the catalog as it
stands, which is the only combination that is true at both ends.

**Delivery is at-least-once, and two places assumed it was exactly-once.** A task can reach a
worker twice. When it did, the second write hit the unique constraint the design leans on and was
logged as a failure, with a stack trace, which reads like data loss and is a duplicate being
refused exactly as intended -- it is now absorbed and counted as seen before. And the watchdog
asked whether `dispatched == handled` before declaring the site exhausted; a duplicate makes
handled run ahead, so a perfectly finished crawl was declared stalled and its index was never
published. It asks whether anything is still owed.

**Emptying a catalog refused to remove the version search was serving.** That guard is right when
somebody names a version -- taking the served one out from under a live search deserves to be said
out loud -- and wrong for the two whole-catalog choices, where all of it is precisely the request.
It refused every empty and every delete on every catalog that had ever finished a crawl. Now it
applies only when versions were named.

**The front end asked for the wrong thing.** Both delete choices sent `keepLatest: 0`, which the
api reads as "every version, by name" rather than "the catalog" -- so both went down the path that
guard protects, and both would have failed even after the guard was fixed. And `purge` was sent
whenever nothing was kept, which is the difference between emptying and deleting: the choice the
operator had just made was being overridden. Emptying and deleting now send what they mean.

**A server logged nothing.** The shared file defaults every level to WARN, which is right for the
prompt -- a live dashboard cannot share a terminal with INFO -- and wrong for a process nobody is
watching. Two hours of this investigation were spent on a node whose only log line was a hibernate
warning. The api's own configuration turns its own package back to INFO.

**The Elasticsearch vector index was never created.** Its mapping put the four fields at the root
of the mapping object rather than under `properties`, and Elasticsearch does not ignore what it
does not recognise -- it rejects the whole request, so the index was never created and every
vector for the run was dropped. The failure was handled gracefully, which is why it was invisible:
the composite channel logged "output 'vector' could not be opened and is skipped for this run" and
carried on, and the crawl finished, published and searched perfectly well with no vectors in it.
The unit test asserted what was sent -- `dense_vector`, the width, the similarity, all of them
present and all of them in the wrong place -- because a stub server accepts any shape. It now
asserts the shape as well.

**A crawl announced it was over before it was.** The permit was released, and the run taken out of
the registry, before the version was published and the old ones pruned. Everything a caller reads
to decide whether a crawl is running said no while it was still writing -- so "delete this
catalog", pressed on a page that said the crawl had finished, answered "version 0 is being crawled
right now", and there was no length of time anyone could name to wait. The order is reversed:
publish, prune, mark the catalog idle, close the stores, release the permit, and only then leave
the registry. What the api reads is the last thing to change, so by the time it says no crawl is
running there is nothing left to collide with.

**On SQLite, a busy database lost the page.** SQLite locks the whole file to write, so two
workers finishing in the same millisecond means one of them is told the database is locked. That
came out of `recordStore.save` as a `CannotAcquireLockException` -- Spring's own word for it is
*transient*, which says what to do about it -- and was caught by the generic handler, logged as a
failure, and the url reported unhandled. Four threads on the six page regression site lost two
pages, and because the counters then never met, the run was declared stalled and published
nothing. The write is now offered again, five times, backing off a little further each time
because the writer being waited for is a worker that will be done shortly. A duplicate is still
absorbed rather than retried: those two are different answers to two different questions, and
telling them apart is the whole of it.

**run-local.sh could not use a database server.** It gives each node its own H2 file, which is
right -- a node keeps a complete copy and replication is what makes the copies agree -- but it did
it by assigning `GF_DB_URL` unconditionally, so a url naming MySQL or PostgreSQL was computed,
exported and then thrown away. The script's own error message tells the reader to "point it at a
shared server which every node can use at once", which the script then would not do. The
command-line launcher had the rule right and says so in a comment; run-local.sh now matches it:
what somebody set stays set, and only what nobody chose is filled in. The guard that refuses
several nodes on one file already covers the case this was protecting against.

**run-docker.sh could not start anything.** Three variables -- `IMAGE`, `NETWORK`, `MEMORY` --
were used and never assigned, and the script runs under `set -u`, so `./run-docker.sh start` died
on its first line of real work with `IMAGE: unbound variable`. Nothing downstream of that had ever
run: not the image build, not the network, not a container. Found by running it, which is the only
way this class of thing is ever found -- a shell script has no compiler, and `set -u` turns a
typo into a runtime failure at exactly the line nobody reads. They are declared beside the ones
that were already there, with the defaults their comments had been describing all along.

**And in Weaviate, `/v1/v1/schema`.** `baseUrl` already ends in `/v1`; one method added it again.
Listing collections would have failed against a real server, which is what a real server was then
started to find out.


## The same url is now fetched once
------------------------------

A finished crawl was reporting "6 dispatched, 10 handled" -- four of ten fetches were the same
pages a second time, refused by the database's unique constraint after they had been fetched,
parsed and fingerprinted. Delivery through the cluster is at-least-once, which is the normal
guarantee and not a fault; what was missing was anything that acted on it.

Three changes, and none of them works without the others.

**Urls are routed by url.** `unicastOn` takes a routing key and a load balancer, and both were
being passed as null -- so the default, round robin, sent the same url wherever the counter
happened to point. 1.x did not do this: every packet it sent carried `partitioner=hash` over
catalogId, refer, path and version. The key is now `catalogId|version|url` (refer deliberately
left out: the same url found on two different pages is exactly what this exists to send to one
place) and the balancer is `consistentHash` rather than the plain modulo 1.x used, so a node
joining moves about 1/N of the urls instead of nearly all of them.

**A frontier queues a url once.** `RocksDbCrawlFrontier` keeps a second key space beside the queue
-- `u:` next to `f:` -- and `put` refuses a url it has already queued. In the frontier rather than
in the channel because every path meets there: a task from a peer, one the dispatcher kept
locally, a sitemap seed, one recovered from the last run. The store is already scoped to this
catalog and version, so it costs one local write per url and nothing in memory. It is forgotten
and rebuilt at the start of each run, from what is still in the queue: what it answers is "has
this run queued it", and a refresh re-queues the very pages the run before it fetched.

**Every dispatch is settled exactly once.** This is what the first two would have broken. Two
nodes can discover the same link inside the replication window and each dispatch it; routed
together, the second is refused by the frontier, and nobody would ever have reported it handled --
so `handled` would sit one short of `dispatched` for ever and the run would be declared stalled
and publish nothing. `CrawlFrontier.put` now says whether it queued, and the three places that
queue answer for what it turned away.

Measured on three nodes and a sixty-one page site, sharing one PostgreSQL:

```
  dispatched : 61                   handled : 66      saved : 61
  node-1: 18 fetched   node-2: 18   node-3: 25        -- 61, each page once
```

Sixty-one pages, sixty-one fetches, spread across three nodes. The gap between handled and
dispatched is redelivery that reached a frontier twice: it costs a count, not a fetch, and the
completion test asks whether anything is still owed rather than whether the two are equal, for
exactly this reason.

An earlier run of the same thing read 161 dispatched for the same 61 pages -- three nodes
discovering a link inside the window before their dedup stores have replicated, and each
dispatching it. It varies with timing, and it is the reason the counters cannot be required to
match: what does not vary is `saved`, which was 61 both times. Those hundred extra dispatches were
stopped at a frontier, not at the database, so they were a hundred fetches that did not happen.


## A finished crawl is announced
------------------------------

1.x published a `WebCrawlerCompletionEvent`, and the audit above recorded 2.0 as not having one --
`ControlMessage` even carried a comment arguing it was unnecessary, because the completion flag
and the reason already live beside the counters and any node can read them whenever it likes.

That argument answers the wrong question. The shared counters hold the **state**, and they still
do -- nothing here duplicates them. What they cannot give is a **moment**. An application that
wants to do something when a crawl finishes had to poll a flag: it hears about it up to one
interval late, and there is nowhere to hang the work.

So `COMPLETED` joins `STARTED` on the control channel, and the shape follows the one that was
already there:

- the node winding the run down announces it **once**. The announcement comes back to its sender
  like every other, so announcing it per node would give every node one event per node.
- every node -- the announcer included, and any that took no part in the crawl -- publishes a
  `WebCrawlerCompletionEvent` locally. Exactly once each, which is what makes `@EventListener` on
  it mean what a reader expects it to mean.
- one process, with no cluster to tell, publishes it directly. `announceCompleted` returns false
  there and the launcher does it itself; a single node is not a degenerate cluster, it is a case
  with nothing to send and nobody to send it to.

It is a notification and not a decision. It is sent after the version is published, the stores are
closed and the permit is released -- nothing in the crawler waits for a listener, and a listener
that throws is logged and stepped over, because somebody else's notification failing is not the
crawl failing. The event carries the catalog, the version, the reason in the same words the
dashboard uses, and whether the run was cut short, which is the one thing a listener is most
likely to branch on.

------------------------------

Two tiers, because they answer different questions.

**Main** is the product's own path, and every choice in it appears at least twice, paired with a

**Secondary** is what a deployment may have and most will not: SQL Server, Oracle, Qdrant,

## Three containers, and three bugs only containers could show
------------------------------

The local three-node run and the Docker one are not the same test. The second exercises what only
containers have: the image, the network, the fixed addresses nodes advertise to each other, and
configuration arriving as environment rather than as a file beside the launcher. Run against the
shared stores a deployment shares -- PostgreSQL, MinIO, Elasticsearch -- because three containers
with three local Lucene directories would each answer a search with the third of the site it
happened to fetch.

```
gfreg-1: 172.29.0.10  members=3  leader
gfreg-2: 172.29.0.11  members=3  follower
gfreg-3: 172.29.0.12  members=3  follower
dispatched 99 / handled 99 / saved 61 / indexed 61
gfreg-1: 26   gfreg-2: 14   gfreg-3: 21      -- 61, each page once
search from gfreg-3, which fetched 21 of them: 5 hits
delete from one node: INDEX 61 / FILE 126 / DB 61
```

**Whether they formed a cluster is now checked before anything is crawled**, by asking each node's
`/actuator/spreader` for `memberCount`. Without that the test was worthless in the way that matters
most: a cluster that never formed still finishes the crawl -- one node does all of it -- and reports
the same numbers.

Three things that had never run:

- **`run-docker.sh start` could not start anything**: `IMAGE`, `NETWORK` and `MEMORY` were used and
  never assigned, under `set -u`, so it died on `IMAGE: unbound variable` before building the image.
  Nothing downstream of that line had ever executed.
- **Every container start downloaded the embedding models again.** `GF_MODEL_DIR` defaulted into
  the home directory, which is not the volume, so a rolling update pulled hundreds of megabytes per
  container and a host without internet access could not start a node at all. It is
  `/app/data/models` now, inside the volume.
- The embedding preload has no reason to run when the catalog does not ask for vectors, which is
  what made the first two visible: three containers sat downloading models past the health-check
  timeout.


## The schema is a script now, not a side effect
------------------------------

`ddl-auto=update` is what a laptop wants and what a production database must not be given. It only
ever **adds**: a column whose type changed is left as it was, a dropped one stays, an index that
was renamed becomes two, and two nodes starting together race to create the same table. None of
that is reported.

So `docs/sql/` holds one script per database -- H2, SQLite, MySQL, PostgreSQL, SQL Server, Oracle
-- and the recommendation is to run one against an empty database and then set `GF_DB_DDL=validate`,
which makes a node refuse to start when the schema and the entities disagree. That is where you
want to find out.

**Generated, not written.** `SchemaScriptsTest` exports them from the entity classes for each
dialect, offline -- no database is opened, so generating the Oracle script does not require an
Oracle. A DDL file maintained separately from the code it describes drifts, and the first anyone
hears of it is a column that exists on one deployment and not another. Change an entity, run the
test, and a modified file in the diff means the schema moved and somebody has to decide what
existing databases do about it.

The PostgreSQL script was run against a real empty schema to check it is not merely plausible:
five tables, five indexes, then dropped again.

## Still open
------------------------------

- The cross-node dedup window is wide: 161 dispatches for 61 pages on three nodes, because each
  node's dedup store is its own and replication between them is not instant. None of them reaches
  a fetch any more -- the frontier stops them -- so what is left is message traffic, and closing
  it further would mean asking the url's owner node before dispatching, which is a network round
  trip per link. Worth measuring before assuming it is worth it.
- SQL Server and Oracle are not in the regression matrix yet. The other four are (H2, SQLite,
  MySQL, PostgreSQL), and the credentials for both are on this machine; only the time is missing.
- `--url` and `--start-url` resolving to the same page can save one url twice and hit the resource
  primary key. Two threads racing the dedup gate on the seed. Now absorbed rather than logged as a
  failure, so this is a waste of one fetch rather than a visible error.
- The `spreader-report` actuator endpoint id contains a hyphen, so Spring Boot warns at every
  startup. It is openspreader's name (`SpreaderReportEndpoint`, the human-readable HTML page;
  `spreader` is the JSON one); we only expose both.
- Whether `update` / `rebuild` / `resume` / `pause` should follow `crawl` into `catalog-*` names.
- A per-catalog analyzer, now that each catalog has its own index. Needs a column and a question.
- `GET /v2/catalog/{idOrName}` still returns the `Catalog` row rather than `CatalogDetails`. Left
  alone deliberately: the edit form needs the stored row, so that a field left blank stays blank
  and keeps taking the default. `/details` is the one that applies them.
