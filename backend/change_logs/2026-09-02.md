## 1. 打错一个名字不该收到 33 行堆栈

`catalog show --catalog nope` 以前是这样的：`CatalogDetailsNotFoundException` 一路穿过
`ApplicationRunner`，被 Spring Boot 的 `handleRunFailure` 当成启动失败打了整段 trace。
消息本身（`No such catalog: nope`）夹在中间，得自己找。

`OneShotCommandRunner` 现在只捕获两类异常：

| 异常 | 为什么是"输错了"而不是"坏了" |
|---|---|
| `WebCrawlerException` | 全部 7 处抛出点的 message 都是写给人看的整句话 |
| `IllegalArgumentException` | `DeleteLayer.parse` / `OutputType.parse` / `ContentMode.parse` 的"Unknown xxx" |

其余异常照旧带堆栈抛出去——**堆栈就是 bug report，不该顺手吃掉**。被捕获的那两类，
堆栈没有丢，降到 debug 级别留在日志里。

```
$ ./greenfinger-cli.sh catalog show --catalog nope    # stderr
No such catalog: nope
Run 'catalogs' to see the names that exist.
$ echo $?
1
```

## 2. 一半的用户错误当时是 exit 0

验第 1 条的时候发现的：真正抛异常的那条路修好了，但另有 8 处用户错误是
`print(Ansi.red(...)); return;`——**打完红字正常返回，退出码 0**。
`greenfinger-cli.sh delete --catalog x || echo failed` 什么也不会发生。

既然这条待办要的就是"一行红字 + 非零退出码"，只修一半没意义。新增
`UsageException extends WebCrawlerException`，8 处改成抛它：

- `crawl` 没给 url 也没给 catalog、`delete` 没说版本、`test-url` 没给 url
- `catalog-show` / `catalog-delete` 没给 catalog、`catalog-save` 没给 url
- `search` 没给 q
- `dispatch` 的 default 分支（未知命令）—— 顺带**不再为一个拼写错误把整页 help 倒出来**，
  改成一行 + "Run 'help' to see every command."。这个分支只有单行命令形态会走到，
  交互式 shell 有自己的未知命令处理，不受影响

多行提示没有丢：`UsageException(problem, ...hints)` 把提示接在 message 后面，
runner 第一行红、其余暗色。

另外两处不是"输错了"而是"做不到"，改抛 `WebCrawlerException`：
`catalog-delete` 删除返回 false、以及向量库不支持图片检索时的 `UnsupportedOperationException`。

退出码怎么出去：`OneShotCommandRunner` 实现 `ExitCodeGenerator`，`GreenfingerCliMain`
在 `run()` 之后取 `SpringApplication.exit(context)`，**只在非零时 `System.exit`**——
成功路径保持原样，仍旧等最后一个非守护线程结束自然退出。

## 3. 图片检索在浏览器里其实一张图都出不来

写前端 e2e 的时候发现的，是这两天最值得记的一条。

9-01 我验 `/v2/image` 时记的是"匿名 401、带 token 200"，当时把 401 当成安全检查通过了。
但页面上的 `<img src="/v2/image?path=...">` **就是匿名请求**——浏览器不会给 img 标签
加 Authorization 头。所以每一张图都是 401，`(error)` 触发，全部退化成
"image_not_supported" 占位符。**curl 验的是接口，不是这条路。**

`ImageApiController` 自己的 javadoc 写着"This is the one call that turns the stored path
into something an `<img>` can use"——意图是对的，实现差了一步。

修在前端（见 frontend 的 log）：不放开鉴权，改由 `HttpClient` 取 blob 再转 object url。
后端只改了那段 javadoc，把"给 img 用"改成"给前端取字节用"，并写明
**为什么不能把这个端点放公开**：那等于把所有归档图片放到登录之外。

## 4. 删掉 `InMemoryCatalogStore`

`CatalogStore` 只有 JPA 一个实现，也只会有这一个——catalog 一律落库，接口的 javadoc 本来
就写着这句。那测试里那个手写的内存替身就只是第二套需要同步维护的规则，而且**已经不同步了**：

`JpaCatalogStore.save()` 补 7 个默认值，内存版只补了 3 个（id / indexVersion / searchVersion），
`outputTypes`、`contentMode`、`maxVersions`、`imageEnabled` 四个没补；
`publishSearchVersion` 不写 `lastIndexed`，`findRunning` 把 `RUNNING_STATE_NONE` 写成字面量
`"none"`。它的 javadoc 却写着"Its behaviour matches the JPA store's"。

这些默认值 `CatalogAdminService` 自己也会补一遍，所以测试一直是绿的——**替身的偏差被
上层的兜底盖住了**，这正是这类替身最难发现的失效方式。

`CatalogAdminServiceTest` 改成 `@DataJpaTest` 打真的 `JpaCatalogStore`（H2），13 个用例全绿。
注解和 `JpaStoreTest` 完全一致，Spring 复用同一个缓存 context，实际没有额外开销。

## 7. 预加载模型是坏的，而且坏得很安静

而且触发条件是"全局默认 output types 含 vector"，默认是 `file`——books2 是在 catalog 上开的

⚠️ 这个改动我自己踩了一次：`ReplayService` / `QueryCommands` / `VectorSearchSupport`

### 撞到的四个真 bug

| bug | 表现 | 为什么难发现 |
|---|---|---|
| 同一个 `CrawlCluster` 实例注册成两个 bean | Spring 把生命周期跑两遍 → `addListener` 两次 → **每个页面爬两遍** | 不报错。只有"消息数是分发数的 2 倍"这一个线索 |

## 11. 一次一个爬取：`WebCrawlerSemaphore` 同时问两个问题

进程内的许可回答"这个进程在爬吗"，catalog 表回答"别的节点在爬别的吗"。两个都要：
许可不知道别的节点，表分不清一个进程里的两个线程。

表就是那个"全集群本来就同意"的地方——每个节点都往里写自己的 running state，每个节点都能读，
不需要锁服务、不需要 leader、没有东西要保活。**同一个 catalog 在跑不算拒绝**，那是节点加入它。

这是检查不是锁：两个节点同一瞬间发命令可能都通过。代价是两个不同 catalog 分掉带宽，
而这正是这条规则想劝阻、而不是想杜绝的事。

顺带修了一个 UX 洞：`POST /v2/crawl/{ref}` 是异步的，返回 "started" 之后才在后台被拒——
**调用方什么都不知道**。加了同步预检，现在会返回：

```
A crawl of 'semA' is already running. One at a time, here and on every other node:
two would divide the bandwidth rather than double it.
Wait for it, or stop it with POST /crawl/semA/interrupt
```

三节点实测：semA 存了 42 页，semB 存了 0 页并被明确拒绝，同一个 catalog 在别的节点上照常加入。

## 12. 集群名隔离：一个真事故

三节点回归到一半，**所有 catalog 在所有节点上凭空消失了**。

原因：一次集群就是"同名 + 同端口的所有人"。`run-local.sh` 的节点、
上一轮遗留还在跑的 docker 容器、以及 8088 上的单节点，用的是同一个默认集群名
`greenfinger-cluster` 和同一个端口 22000——**三个测试环境合并成了一个集群**，
于是 e2e 清理时发出的删除跨环境传了过去。

这不是测试环境的偶然：任何一台机器上跑两套 greenfinger，默认配置下就会合并，
而它们发现这件事的方式是互相复制对方的写入，包括对方的删除。

改法：`run-local.sh` 用 `greenfinger-local`、`run-docker.sh` 用 `greenfinger-docker`、
plain 启动器保持默认，三者互不相干；README 里加了一段醒目提示，
说明 `GF_CLUSTER_NAME` 在多套部署的机器上不是可选项。

清干净之后同样的场景跑了 15 秒，三个节点的 catalog 列表一直稳定。

## replay 分布式化

爬取是 fork 无 join，replay 是这个系统里**唯一**真正的 scatter-gather：范围有界（数据库里就
那么多行）、一次性 fan-out、幂等、而且需要知道全部做完才能返回。所以它走 openspreader 的
`ProcessingPool`，而不是爬取那条 gossip 通道。

`ReplayService.replay` 拆出了 `replaySlice(catalogId, version, layers, offset, limit)`，
单机就是 `replaySlice(..., 0, MAX_VALUE)`。`ClusterReplayService` 覆盖 `replay`，把总数切片、
`pool.submit(beanName, "replayRange", ...)` 发出去、逐个 join；`replayRange` 上标
`@MultiProcessingCall`，收到的节点解析自己的 bean 执行。跨网络的只有五个值——catalog id、
version、层名、offset、limit——一个对象都不传。

**分片大小卡在两个边界之间**，这一点踩了两次才对：

- 一开始按节点数切（`总数 / (节点数 × 3)`）。逻辑上很自然，但灾难性地错了：目录越大，每片越大。
  176 页切成 4 片没问题，10 万页就会切成 1.1 万页一片，**每一片都会超时**。
- 于是改成固定 200 页一片。不超时了，但 176 页只切出 1 片、发给 1 个节点，另外两个闲着——
  正确但没并行。
- 最后是两个边界一起卡：`clamp(总数 / (节点数 × 3), 50, 200)`。上界保证一片能在池的等待时间
  内跑完（不管目录多大），下界保证一片值得一个来回，中间按节点数铺开。

**超时**：`spring.spreader.multiprocessing.pooling.request-timeout-ms` 默认 10 秒，那是给
"很快就返回的调用"用的。一片 200 页的 embedding 是几十秒，所以第一次跑直接
`远端 ... 执行失败或超时`，而且——`MultiProcessingProperties` 的注释写得很清楚——递归任务超时
会退回本地重算，**方法调用超时是直接抛异常**。改成 120 秒：够长，不会放弃一个还在干活的节点；
够短，一个死掉的节点不会把整个 replay 拖住。

**丢片就在本地做**。哪一片没回来（节点没了，或者超过了池的等待），不构成 replay 失败——
`collect()` 捕获后原地 `replaySlice` 同一个区间。这条之所以安全，正是因为 replay 幂等：
下游每个 id 都是自然键的 name-based UUID，就算远端其实做完了，本地这一遍是**盖在**它上面而不是
并排新增一份。慢一点，但完整——对一个"人为了修东西才会去跑"的操作，这个取舍是对的。

**实测**（本机 3 节点，rp2 = 176 页）：删掉 index + vector（ES 176→0、text 477→0、
image 1172→0），`POST /v2/crawl/rp2/replay?layers=index,vector` 之后回到 176 / 477 / 1172，
日志 `Replaying 176 page(s) ... across 3 node(s) in 4 slice(s) of 50`，分片确实落在不同节点上。

耗时 64 秒，和单节点跑完全部的 60 秒**几乎一样**，这不是 bug：三个节点在同一台机器上，
embedding 是 CPU 密集的，分片再多也是在抢同一批核。分布式 replay 的收益要在**多台机器**上
才会出现。

### replay 也能还原文件了

一开始我判断 replay 不能还原文件——数据库里没有网页正文和图片字节，`replaySlice` 第一行就是
`targets.remove(OutputType.FILE)`。Fred 指出这个判断是错的：**数据库里有 `resource.url`，
`resource_image` 里有 `source_url`**，所以文件不是"无从还原"，是"要重新去取"。

于是有了 `FileRestorer`。它是**窄义上的爬取、广义上不是**：会发请求，但不发现任何东西——
不跟链接、不写行、不访问任何不在表里的 url。URL 集合在第一个请求之前就固定了，这才让它是"修复"
而不是"再爬一遍"。

- **先文件，再索引和向量**，顺序是硬性的：后两者的正文是从 blob store 读回来的，文件还没回来
  就重建索引，会静默地索引出一堆只有标题的空页（缺文件读作空，不读作错）。所以一次
  `--layers file,index,vector` 能把一个版本完整修好。
- **文件齐全的页面直接跳过，一个请求都不发**。这让操作可以放心跑第二遍，而且第二遍很便宜。
- **礼貌间隔白拿**：用的是 catalog 自己的 `componentFactory.getExtractor(...)`，
  `ThreadWaitExtractor` 里的 `fetchInterval` 照样生效。修东西不是对还活着的站点无礼的理由。
- **图片按行里记的路径写回**，不是按取回来的字节重新算路径——那个路径是索引和向量引用这张图的
  方式，恢复必须落在它上面。`ImageFetcher` 加了 `fetchOne(url, pageUrl)`，跳过基于 markup
  声明尺寸的预筛（恢复时没有 markup，只有一行"这张图当初存过"），但保留大小和类型上限。
- **取回来的是今天的站点**。页面变了，恢复的就是新正文，跟当初建索引的旧正文对不上——所以恢复
  文件之后通常要接着 replay 另外两层。页面下线了则根本恢复不了。两种情况都计数上报
  （`unreachable` / `changed`），静默留洞比失败更糟。`changed` 是按 `text_length` 比的，
  是**提示不是证明**：长度没变的改动抓不到，但抓到的一定是真的改了。

**一个必须一起改的坑**：`OutputType.parse` 会把 FILE **无条件**加进结果（爬取时"文件层不可
关闭"是对的，否则其他层没有输入）。照旧用它，`replay --layers index` 会连带重新抓全站。所以
新增了 `parseExact`，replay 路径改用它——文件层只有被显式点名才会动。

CLI 的 `replay` 现在会多打一行文件恢复的统计；前端菜单加了 "Restore missing files from their
urls"，删除确认里那句"文件删了就无法 replay 回索引"也改成了准确的说法。

**这一层不能切片分发**，和 index/vector 正相反。文件是每个节点一份全量，"缺什么"在每个节点上是
不同的答案：拿到分片的节点检查的是**自己**的文件（完好），于是报告无事可做，而真正丢了文件的节点
根本没被问到。所以走 control 通道多播 `RESTORE_FILES`，**每个节点修自己那份**；发起的节点已经
先修过自己，靠消息里带的 origin 跳过回声。完好的节点一个请求都不发，这才让"问所有人"是便宜的。

**实测**（本机 3 节点，rp2）：删掉 **node-2** 的 40 个 html + 40 个 txt + 100 张图，把请求发给
**node-1**（完好的那个）——这正是切片做法会漏掉的场景。node-1 检查 176 页全在、0 请求、立即返回；
node-2 后台自修，150 秒后 180 个文件全部回来，抽查的文件与 node-1 的副本**逐字节一致**
（11991 / 11991），node-2 自己的报告是
`40 page(s) and 100 image(s) written, 94 already there, 0 unreachable, 0 changed since the crawl`。
（intact 是 94 不是 136，因为那 100 张图分散在另外 42 个页面上，那些页面的 html 在、图不在，
所以也要取。）

### 顺带修掉的一个真 bug：删除目录不会停掉它的爬取

e2e 回归时发现 crawl 被一个**已经不存在的目录**拒绝。查下来：爬取从 frontier 取下一个 url，
不看 catalog 表，所以**把行删掉不会让它停**。它继续抓一个不存在的目录，同时从 running 列表里
消失了（列它的那行没了），而它占着这个进程唯一的许可**永远不还**——之后这个节点上的任何爬取都会
被一个谁也看不见、叫不出名字的爬取拒绝。现场证据：一个 14:29 启动的进程到 15:40 还在 33% CPU
上抓一个删掉的目录。

`CatalogAdminService.delete` 现在先 `crawlRegistry.interrupt(id)` 再删行。是"请它停"不是"杀掉"，
在途的东西照样写完；集群里其他节点照常从 control 通道听到。

## greenfinger-cli 支持 -n（傍晚）

`run-local.sh` / `run-docker.sh` 起的都是 **greenfinger-api**（web 服务，每个节点自带前端静态资源，
`/` 直接返回页面，不是"n 个后端 + 1 个前端"）。`greenfinger-cli` 之前只有单进程，现在也支持 `-n`：

```
./greenfinger-cli.sh -n 3        # 一个 prompt + 两个无头 worker，同一个集群
```

- **shell 就是节点 1，并且保留它原本的数据目录**。这一点和最初的设想改了：如果节点 1 也拿一个
  新的 `cli-1` 目录，`-n 3` 会让你之前爬的东西集体"消失"。worker 各自拿 `deploy/workers/cli-N`，
  放在 data 目录**旁边**而不是里面（嵌在里面会被节点 1 的文件遍历扫到）。
- **worker 模式**是 CLI jar 加 `--greenfinger.cli.worker=true`：不进 shell、常驻、只做集群成员。
  常驻靠的是 `ApplicationRunner` 里阻塞——和交互式 shell 保持进程存活是同一个机制。用非守护线程
  不行：`SpringApplication.exit` 在 main 拿到控制权的那一刻就会关掉上下文。
- 就绪信息走 **stdout 而不是 log**：`com.github.greenfinger` 默认 WARN，一个只有日志文件能看的
  后台进程，不该依赖"有人先把级别调上去"才肯说自己起来了。
- shell 退出时 trap 把 worker 一并停掉（是"请它停"不是 kill -9，在途的页面照样写完）。

**实测**：`greenfinger-cli.sh -n 3 crawl -u books.toscrape.com --max-size 30`，两个 worker 都打了
`Worker node ready`，三个节点各 33 页（复制一致），shell 退出后 0 残留进程。

### 短选项：-n 让给启动器，catalog 名字改成 -c

`-n` 原来是 `--name`（catalog 的名字），和启动器的"起几个进程"冲突。按 Fred 的要求改成 `-c`；
`--config` 让出 `-c`，只保留长名（配置文件路径是粘贴的，不是敲的）。

顺带发现 `CommandLine.expand()` 和 `@Option` 注解**早就不同步了**，而且是静默失效：

- `-o` 展开成 `output`，而下游读的是 `outputTypes`（normalize 后 `outputtypes`）——**`-o` 在
  一次性模式下一直是被忽略的**，写进去没人读。更糟的是旧测试 `parsesShortNames` 断言的正是
  `get("output")`，把 bug 固化住了。
- `-t` 展开成 `to`，而根本不存在 `--to` 这个选项。
- `-f` 展开成 `from`，但 `--from` 没有 `shortName`，所以 `-f` 只在一次性模式有效、交互式无效。

原因是有**两个解析器**：交互式走 spring-shell 自己的（读 `@Option`），命令行一次性走
`CommandLine.parse`（自己维护一张字母表）。两者漂移不会报错，只会让选项被忽略。现在加了
`CommandLineShortNameTest`：反射扫出所有 `@Option` 的 `shortName`，逐个 `-x value` 解析，断言能
用注解上的 longName 读回来。靠测试而不是靠注释保持同步。

最终五个字母：`-u` url、`-c` name、`-k` catalog、`-o` output-types、`-f` from。
