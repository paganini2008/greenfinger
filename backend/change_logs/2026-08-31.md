# 2026-08-31 · backend

服务端从"只能被嵌入的 starter"变成一个可独立运行的 web 应用，并加上了登录。

---

## 1. `greenfinger-spring-boot-starter` → `greenfinger-api`

目录、artifactId、包名一起改：`com.github.greenfinger.starter` → `com.github.greenfinger.api`。

不只是改名，性质也变了：

- 新增 `GreenfingerApiMain`（`@SpringBootApplication` + `@EnableGreenfingerServer`）
- `spring-boot-starter-web` 从 `optional` 变成必需 —— 这个模块**就是**服务端；不需要 servlet 容器的是 `greenfinger-cli`，它仍然只依赖 `greenfinger-core`
- 带上和 CLI 一样的驱动与引擎（H2 / PG / MySQL / SQLite、htmlunit、MinIO、DJL），因为从浏览器建的 catalog 必须能爬和存下命令行能爬和存的一切
- `spring-boot-maven-plugin` 打包 + 装配到 `deploy/`，多出 `greenfinger-api.sh` 与 `greenfinger-api.jar`

`@EnableGreenfingerServer` 保留，仍然是显式启用，不走 `META-INF` 自动装配。

## 2. 登录：Spring Security + 不透明 token

新增 `com.github.greenfinger.api.security`：

| 类 | 干什么 |
|---|---|
| `GreenfingerSecurityProperties` | `greenfinger.security.*`，全部来自 `.env` |
| `PreAllocatedUsers` | 解析 `username:password:role`，单独一个类是为了不启容器就能测 |
| `TokenStore` | 内存 token，签发 / 解析 / 吊销 / 滑动续期 |
| `TokenAuthenticationFilter` | 读 `Authorization: Bearer`，认不出就保持匿名，交给授权规则判 |
| `WebSecurityConfiguration` | 过滤链、两个角色的授权规则、CORS、401/403 的 JSON 出口 |

接口：`POST /v2/login`、`POST /v2/logout`、`GET /v2/me`。

**为什么不是 Basic**：1.x 用的是 Basic，它的 `/logout` 是个空方法 —— 没有真正的登出。
**为什么不是 session cookie**：单页应用要处理 CSRF 与跨域 cookie，为一个内网管理台引入两类容易配错的东西。
**不透明 token**：logout 就是从 map 里删掉，立刻失效；无 cookie 即无 CSRF。内存持有，重启全部登出 —— 对"两个预分配账号的运维工具"这是正确的取舍。

一次登录一个 token（不是一个账号一个），所以 A 浏览器登出不影响 B。每次请求续期，所以盯着几小时的爬取任务不会中途被登出。

两个角色，规则只有一条：**GET 放行给两者，其余需要 ADMIN**。默认账号 `admin/admin123`（ADMIN）与 `tester/tester123`（SUPPORT），来自 `.env` 的 `GF_USERS`。

## 3. 配置结构重整

原先按数据库拆的 `application-mysql/pgsql/sqlite.yml` 删掉，改成三个文件，**CLI 与 web 共用同一份**：

- `application.yml` —— 公共部分，外加只有服务端会用的 `server.*` 与 `greenfinger.security.*`
- `application-dev.yml` —— 零配置，默认：H2 文件库、本地磁盘、`types: file`
- `application-prod.yml` —— 真实部署：`GF_DB_*` 必填，故意没有兜底；三条输出全开

四种数据库的连接串写在 `application-prod.yml` 的注释里。只有 SQLite 需要 `GF_DB_DIALECT` —— Hibernate 本体不带它的方言。

`.env.example` 补上 `GF_PROFILE`、`GF_SERVER_PORT`、`GF_USERS`、`GF_TOKEN_VALIDITY`、`GF_CORS_ORIGINS`、`GF_DB_DIALECT`。

## 4. 新增接口

| 接口 | 说明 |
|---|---|
| `GET /v2/version` | 免登录。登录页要显示它，而"是哪个版本拒绝了你的密码"正是发现连错服务器的方式 |
| `GET /v2/catalog/{ref}/summary` | 改为返回 `CatalogSummary`：在跑就给实时 dashboard，没跑就从 `settings.json` 的 `lastRun` 读回来，**两条路同一个形状** —— 任务刚跑完不该让正在看的页面变空白 |
| `GET /v2/catalog/{ref}/running` | 单个 catalog 是否在跑 |
| `GET /v2/image?path=` | 取回爬下来的那张图。见下面第 4.1 节 |
| `GET /v2/search/semantic` | 语义检索（文本向量） |
| `GET /v2/search/images` | 以文搜图（图片向量） |
| `GET /v2/search?cursor=` | 关键词检索加上 cursor 参数，绕开 ES 一万条上限 |

### 4.1 图片接口：为什么不能直接用原始地址

图片本来就爬下来存好了，问题在于 `imageFilePath` 是 **blob store 的路径**
（`{catalog}/v0/images/ab/cd/{id}.jpg`），不是浏览器能取的 URL —— 所以图片搜索一直没东西可显示。

两条路都补上了：

- **展示用归档的那份**（`GET /v2/image?path=`，从 BlobStore 读字节）。归档本来就是为了这个：
  站点改版、删图、防盗链、http 图片在 https 页面上变成 mixed content，这些都影响不到它；
  也不会把看结果的人的浏览器暴露给每一个被爬过的站点。
- **原始地址也带上**：`VectorOutputChannel` 的图片 payload 新增 `imageUrl`
  （取自 `ResourceImage.sourceUrl`），前端做成"see it in place"链接。
  注意这个字段要 `replay --layers vector` 之后旧数据才有。

路径是调用方给的，所以**按 layout 实际产出的形状校验**，而不是去扫 `..` ——
黑名单要预判每一种编码，白名单只需要描述一个文件名模式。扩展名也写死成图片那几种。

另外加了两个响应头：这些字节来自别人的网站、却从我们自己的 origin 提供，正是 XSS 的形状。
`X-Content-Type-Options: nosniff` 挡住被当脚本执行，`Content-Security-Policy: default-src 'none'; sandbox`
让带脚本的 SVG 失效 —— 两者都不影响 `<img>` 正常画出来。

`VectorSearchSupport`：整个服务端**共用一个 embedding client**，首次搜索时才建、进程退出时销毁。命令行每次命令建一个然后丢掉是对的（进程马上就退出），服务端不能这么干 —— 本地模型加载要几秒和几百 MB，每请求一次会让搜索完全不可用。

## 5. 托管前端

`SinglePageAppConfiguration`：不是文件、也不是 api 的路径回落到 `index.html`，否则在 `/catalogs` 上刷新就是 404。同时找 `classpath:/static/` 与 `file:./static/`，换前端不用重打 jar。

顺带修掉一个真问题：**api 前缀下不存在的路径原本返回 500**。`NoResourceFoundException` 不继承 `ErrorResponseException`，掉进了兜底 handler。现在它返回 404，`ErrorResponseException` 也各自保留自己的状态码 —— 一个拼错的 url 不该被报告成服务端故障。

## 6. 打包显示版本

父 pom 加 `maven-jar-plugin` 的 `addDefaultImplementationEntries`，把版本写进 MANIFEST；`spring-boot-maven-plugin` 加 `build-info` goal 生成 `build-info.properties`。

在此之前 banner 里的 `${application.version:2.0.0-SNAPSHOT}` 一直用的是兜底字面量 —— 2.1 的 jar 也会自称 2.0，而 banner 恰恰是最容易被人相信的地方。现在 CLI 与服务端启动横幅、`/v2/version` 都来自构建。

## 7. 测试

`greenfinger-api` 模块共 44 个用例，全项目 568 个：

- `PreAllocatedUsersTest` —— 账号解析，含拼错时**启动即失败**而不是第一次登录才失败
- `TokenStoreTest` —— 签发、吊销、过期、一次登录一个 token
- `SecurityIntegrationTest` —— 走真实过滤链：401 / 403 / token 跨请求 / 登出后立即失效 / SUPPORT 只读
- `CatalogSummaryTest` —— 实时与 `settings.json` 两条路，含被中断的任务、缺字段的旧文件
- `SinglePageAppTest` —— 深链接回落，以及 api 404 不能变成页面
- `ImageApiIntegrationTest` —— 真的吐出字节、安全头、版本删掉后 404 而不是 500，
  以及七种非法路径（穿越、绝对路径、编码穿越、非图片扩展名、非 uuid）全部拒绝
- `VectorSearchSupportTest` —— 模型建不起来时不留半成品

`WebApiIntegrationTest` / `CrawlApiIntegrationTest` 显式设 `greenfinger.security.enabled=false`：这两个类测的是接口做什么，不是谁能调；谁能调由 `SecurityIntegrationTest` 端到端测，顺带也覆盖了 `GF_SECURITY_ENABLED=false` 这条部署路径。

覆盖率：core 81.2%、api 91.1%、cli 84.1%，`mvn verify` 通过。
