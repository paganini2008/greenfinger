## 4. SQLite：查出并修好了一个真 bug

**症状**：按 `application-prod.yml` 注释配好 SQLite 跑爬取，12 页只存下 1 页，72 次
`SQLITE_BUSY`。也就是说"支持四种数据库"这句话，对 SQLite 是假的。

**排查过程**（每一步都实测）：

| 配置 | SQLite 错误 | 存下的页 |
|---|---|---|
| 默认（16 线程） | 72 | 1 / 12 |
| 加 `journal_mode=WAL&busy_timeout=30000` | 345 | 4 / 12 |
| 上面 + `maximum-pool-size=1` | 0 | **0** —— 连接饥饿，15 个线程等一个连接等到 30 秒超时 |
| 上面 + `transaction_mode=IMMEDIATE` | 16 | 0 —— 和 Hibernate 的 autocommit 管理打架（`cannot rollback - no transaction is active`） |
| 2 线程 | 95 | 4 / 12 |
| **1 线程** | 80 | 0 |

单线程也有 80 次冲突，这条把方向定死了：**问题不在并发**。错误码是 `SQLITE_BUSY_SNAPSHOT`
（"另一个连接已经写过了"），来自**同一个线程内的事务嵌套**。

**根因**：`ImageWriter` 用 `PROPAGATION_REQUIRES_NEW` —— 每张图片的 `findOrCreate` 开一个
新事务，而外层 `save()` 的事务同时开着。在 SQLite 上这就是两个连接同时访问一个文件：外层持有读快照，
内层写入，外层再写就撞上过期的快照。H2 / PG / MySQL 都没事，SQLite 必然出事。

`REQUIRES_NEW` 本身是有理由的（见 `ImageWriter` 的类注释：PostgreSQL 在约束冲突后会中止整个事务），
但那个理由在 SQLite 上不成立 —— SQLite 允许语句失败后事务继续。所以：

- `ImageWriter` 多一个 `ownTransactions` 构造参数，SQLite 上传 false，图片行加入页面的事务
- 判断放在 `GreenfingerRecordConfiguration`，从 `spring.datasource.url` 读，**不开数据库连接**
- 新增 `SqliteConnectionPoolCustomizer`：url 上自动补 `journal_mode=WAL` 与 `busy_timeout=30000`
  （用户自己写了的就不动）。放在代码里而不是注释里 —— 四种数据库共用一套默认值，
  需要不同默认值的那一种不能指望自己开口

**修完实测**：

| 配置 | SQLite 错误 | 存下的页 |
|---|---|---|
| 16 线程 | 26 | **13 / 12** |
| 4 线程 | 6 | **13 / 12** |

剩下的冲突是 SQLite 的固有特性（写事务竞争），爬虫会重试，不丢页。`application-prod.yml` 和
`.env.example` 里写清楚了：SQLite 配 `GF_WORK_THREADS=4`。

## 5. `models pull` / `models list` / `--offline`

底层 `ModelStore` 本来就支持 offline，而且它的报错信息里已经写着"用 `models pull` 取"——
但那个命令并不存在。补上：

| 命令 | 干什么 |
|---|---|
| `models list` | 哪些权重文件已缓存、各多大 |
| `models pull [--layers text\|image]` | 提前下载。只拉文本塔是 129MB，两塔是 522MB |
| `--offline` | 禁止下载，缺文件立刻报错 |

三处细节：

- **文件清单只写一份**。新增 `ModelFile` record，`LocalEmbeddingClient` 的加载路径和
  `models pull` 用的是同一批常量（`requiredFiles()`），不会各自维护一份然后漂移
- **`--offline` 翻译成属性**。model store 在构造时读这个值，那时命令早就跑起来了，
  所以 `CommandLine.toSpringArguments()` 在 Spring 启动前把 `--offline` 变成
  `--greenfinger.embedding.offline=true`，原参数保留，命令解析不受影响
- **offline 时 pull 直接拒绝**，并说清楚正确做法（在有网的机器上 pull，把 `GF_MODEL_DIR` 拷过去）。
  pull 的意思就是下载，偷偷忽略 offline 会让这个开关变成谎话

踩了一个坑：方法名 `list()` / `pull()` 和 `CatalogCommands.list()` 撞了 bean 名，
启动即失败（`The bean 'list' could not be registered`）。改成 `listModels()` / `pullModels()`。

## 6. 条件请求（`If-None-Match` / 304）

merge 时把上次的 ETag 递回去，让站点回答"没变"而不是重发整页。

- `ConditionalGet` / `FetchedPage` 两个 record；`Extractor.fetch(..., conditions)` 是
  **default 方法**，默认就是普通 GET 并报告"没有 validator"
- 只有 `RestClientExtractor` 真正实现 —— 浏览器引擎驱动的是页面加载，根本看不到响应。
  假装支持等于虚报一个并不存在的节省
- `RetryableExtractor` / `ThreadWaitExtractor` / `AdaptiveExtractor` 都显式转发。
  **这一步是必须的**：包装器如果落回 default，会悄悄把条件请求变回普通请求，而且看起来一切正常
- `resource` 表加 `etag` / `last_modified` 两列，存的是站点自己发的值
- 可以关：`GF_CONDITIONAL_GET=false`，给那种"页面变了 ETag 不变"的站点用

### 6.1 顺带修掉一个更早就存在的问题

第一版做完，测试发现三个页面只有 1 个走了 304。原因很简单也很致命：**304 没有 body，
就没有链接可跟随**，于是第一个未变的页面直接终结了整个遍历。

但这不只是条件请求的问题 —— 它暴露了 merge 本来就有的一个洞：**`update --refresh` 是靠从入口
重新爬链接来找到已知页面的**。一个从站点导航里被拿掉、但还在站上、还在索引里的页面，
以前就已经永远不会再被 merge 了，只是没人发现。

所以改成：refresh 开始时，把上次爬到的每个 url 直接入队（`seedFromLastCrawl`，分批 500 条读）。
"重访已知页面"这件事，本来就该从已知列表来，而不是靠重新发现。新页面仍然靠链接发现，两者并存。

改完 3/3 走 304，两个新用例覆盖"全部未变"和"其中一页 validator 变了"。

## 7. 向量检索加 offset 翻页

`VectorStore.search` 加 offset 重载（旧签名成为 default，委托 offset=0），Qdrant 传 `offset`，
Weaviate 拼 `offset:`。`/v2/search/semantic` 和 `/v2/search/images` 加 `offset` 参数，上限 1000。

**用 offset 而不是 cursor**：向量检索没有稳定的排序键可以往下传 —— 那个顺序是"到这条查询的距离"，
只对这一次查询存在。这也是为什么要设上限：offset 越深，向量库要走的路越长。

一个细节：文本检索的 offset **不下推**，因为重排和"一页一条"都发生在向量库应答之后 ——
下推会跳过那些本来就要被去掉的行，第二页起点就错了。图片检索没有重排，直接下推。

## 8. 图片检索质量：实测了，结论不好看但很清楚

先做了一版可判定的评测：books2 的每张封面都带书名作为 alt，书名也印在封面上，
所以"用书名搜，能不能搜到那张封面"有标准答案。25 条查询：

```
recall@1 : 4%      recall@5 : 12%     recall@10: 16%     MRR: 0.084
```

而且总是返回同几张图。第一反应是实现有 bug（两个塔没对齐），于是加了
`CrossModalAlignmentIT`（`-Dgreenfinger.models=true` 开）—— 用纯红和纯蓝两张图问
"a solid red square"，答案不该有争议：

**对齐是好的。** 红查询选红图，蓝查询选蓝图，同图两次编码余弦 1.0，异图不塌缩。

所以低 recall 不是 bug，是**任务本身不成立**：books.toscrape 的封面是 103×155 的缩略图，
缩到 224×224 之后封面上的字根本不可读，SigLIP 没法据此匹配；而所有封面在它眼里都是
"一本书的封面"，彼此差异极小，于是排序被少数视觉突出的封面主导（分数全挤在 0.13–0.15）。

换成**描述画面**的查询就完全不同。用 `sips` 把返回的封面缩成 1×1 读平均色，客观判定：

| 查询 | top-5 主色命中 |
|---|---|
| a red book cover | 4/5 偏红 |
| a green book cover | **5/5 偏绿** |
| a blue book cover | 4/5 偏蓝 |
| a black and white photograph on the cover | **5/5 灰度**（R≈G≈B） |

**结论**：以文搜图适合描述画面内容（颜色、构图、主体），不适合"用书名找封面"——
那需要 OCR 能力，而缩略图分辨率不够。这一条该写进用户文档，而不是留着让人自己撞。
