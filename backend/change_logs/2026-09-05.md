========================================

Seven defects found by running the thing
========================================

The day began as a screenshot session -- three nodes, a real site, take some pictures for the
README -- and every defect below was found by using the product rather than by reading it. That is
worth saying up front, because most of them had been in the code for weeks and none would have been
found by a test that was written to pass. The last one was found by deleting the day's test data,
which is a good argument for cleaning up through the product rather than with `rm`.


## 1. robots.txt was fetched without a user agent
------------------------------

`UrlUtils.openStream` built a bare `URLConnection` and set two timeouts. It set no headers, so Java
sent `Java/17.0.2` as the user agent, and a number of large sites -- Wikimedia among them -- answer
that with 403 before looking at the path.

The failure mode is the worst one available:

```
WARN  RobotRuleUrlPathAcceptor  https://en.wikinews.org/robots.txt is not available,
                                crawling without robot rules.
```

robots.txt came back unreadable, the acceptor fell back to "no rules" the way the protocol says it
should for an *absent* file, and the crawl went ahead ignoring rules the site was publishing all
along. The one request that decides whether we are allowed to crawl was the one that did not
introduce itself.

`openStream` now sends one of the same `WebCrawlerConstants.USER_AGENTS` the extractors use, plus
`Accept` and `Accept-Language`. Same fix covers the sitemap fetches in `SitemapSeeder`, which had
the same hole.

The warning was also reworded. "not available" covers two different things and the difference is
the whole point: a 404 is a site with no rules, a 403 is a site with rules we failed to ask for
properly. It now names the cause.

`RobotRuleUrlPathAcceptorTest` is new and tests the actual scenario: a server that serves
robots.txt only to a caller whose agent starts with `Mozilla/`, and 403s everyone else.


## 2. A jpeg was stored as a page, and indexed
------------------------------

`RestClientExtractor` checked the status code and never the content type. Sites link straight at
their own pictures -- apod.nasa.gov links every day's photograph that way -- and such a link is in
scope, passes every filter, and answers 200.

What that produced, from a 124-page crawl:

| url | title | textLength |
| --- | --- | --- |
| `.../image/2609/2026Eclipse_WB57GoPro_Totality_H264_Abridged.jpg` | `''` | 569,316 |
| `.../image/2609/noirlab2621a.jpg` | `''` | 214,696 |

Half a megabyte of jpeg, decoded as text, written to disk as a page's `.txt`, counted against
`maxFetchSize`, and put into the search index.

`requireMarkup` now refuses anything whose `Content-Type` is not html, xhtml, xml or plain text,
and refuses it as an `ExtractorException` -- for a crawler of pages, a picture at the end of a link
is exactly an invalid url. A missing Content-Type is still allowed through: it is rare, it is
usually html, and refusing it would drop pages from servers that are merely old.

Verified by re-running the same crawl: 0 rows whose url is a file (was 2), 0 empty titles (was 2),
and the two urls named above in the log as

```
Refused 'https://apod.nasa.gov/apod/image/2609/noirlab2621a.jpg':
        the server answered with image/jpeg, which is not a page
```


## 3. A replay rebuilt the index and left it invisible
------------------------------

`searchVersion` is set in `CrawlerLauncher`'s `finally`, under `completed && publisher`. A crawl
whose designated publisher goes away between the last page and that line leaves a catalog with
every row, every file and a `searchVersion` of -1 -- and search skips it.

Replay was the obvious repair and did not repair it. It rebuilt the index perfectly and published
nothing, so the documents were there, they matched, and search returned zero. Before today the only
way out was crawling the whole site again.

`ReplayService.publishReplayed` now publishes the version a replay rebuilt, and never backwards: a
catalog serving v3 that has v1 rebuilt keeps serving v3. `ClusterReplayService` has to call it too
-- the sliced path returns without going through `super.replay`, so a replay spread across the
cluster published while the same replay on one node did not.

Three tests, including the "replaying an older version never demotes" case.


## 4. There was no counter for the vector output
------------------------------

`INDEXED_RESOURCE_COUNT` counts what reached the search index. Nothing counted what reached the
vector store, so a crawl with both outputs on reported the healthy one and said nothing about the
other -- and the vector side is the slower and the more fragile of the two: an embedding model has
to load, a collection has to exist with the right dimension.

`VECTORED_RESOURCE_COUNT(10, "vectoredResourceCount")` is new, incremented beside its counterpart
in `CrawlerEngine`, and carried through `Dashboard`, `DefaultDashboard`, `ReadonlyDashboard`,
`ClusterDashboard`, `CatalogSummary` and both crawl reports.

The shell shows both now -- `Pages indexed` and `Pages vectorised`, unconditionally, because
`DashboardRenderer.lineCount()` derives the redraw height from the table and two zeros on a
file-only crawl say exactly what they mean.


## 5. The default crawl duration was 30 minutes
------------------------------

`defaultFetchDuration` is now 10. Thirty minutes is a long time to wait to find out that a crawl
was pointed at the wrong url, and every launcher takes `GF_FETCH_DURATION` for the cases that want
longer.


## 6. Not a defect: the url is the boundary
------------------------------

`StartUrlPrefixUrlPathAcceptor` uses `startUrl`, falling back to the catalog's url, as a prefix.
A catalog created with `https://en.wikinews.org/wiki/Main_Page` therefore has exactly one page in
scope: 646 links were extracted, 646 were filtered out, one page was saved, and the crawl reported
success. Working as designed and as documented on the form -- but the shape of the mistake is easy
to make and impossible to see afterwards, so it is now called out in `deploy/examples/catalogs.json`
and in the README's table of example sites.


## 7. Open: a delete only reaches the node that ran it
------------------------------

Found while clearing the day's test data, which was itself the point of clearing it that way.
Four catalogs, three nodes, deleted through the front end and through the api. Everything reported
success, and this was left on disk:

```
node-1/user/index/greenfinger-...1fe2       1.0M     Rust Blog      (deleted via the UI)
node-2/user/index/greenfinger-...1fb3       2.7M     APOD
node-2/user/index/greenfinger-...1fc9       249M     Hackaday
node-2/user/index/greenfinger-...1ffd       1.1M     Wikinews
node-3/user/index/…all four…                253M
```

507 MB of Lucene segments for catalogs that no longer exist in any database, referenced by nothing
and cleaned up by nothing. The frontier stores show the same shape: each node kept the RocksDB
directories of every catalog it did not personally delete.

The pattern names the cause exactly. node-1 has only Rust Blog's leftovers -- Rust Blog is the one
deleted through the front end, which round robins, so another node executed it. node-2 has the
three I deleted against node-1 and not Rust Blog's, so node-2 executed that one. node-3 executed
none and kept all four.

**Deleting is a local operation against node-local stores, and the cluster is never told.** The
database rows and the blob files go through replicated stores and are correct everywhere. The
Lucene index, the Lucene vectors, the frontier and the dedup filters are each node's own, and
`DeletionService.deleteIndex` asks this node's `IndexAdmin` and stops.

It does not corrupt anything and it is invisible from the api -- search is gated on the catalog
row, which is gone everywhere, so no stale result is ever returned. It is a disk leak, and on a
three node cluster it is two thirds of every index ever built.

Worth saying: **with Elasticsearch or Qdrant this does not happen.** Those are one shared store
that every node points at, so one delete is the whole delete. It is the embedded providers --
`index.provider: lucene`, `vector.store: lucene` -- that give each node a copy of its own.

Not fixed today. The shape of the fix already exists: `CrawlCluster.announceRestoreFiles` sends a
`ControlMessage` on the control channel and every node repairs its own file store, and a delete
wants the same announcement and the same "every node hears it, including the one that asked" guard.
That is a new control message, a handler, the wiring and its tests, and it was the end of a long
day.

Cleared by hand for now:

``` shell
rm -rf deploy/data/node-*/user/index/greenfinger-<id>
rm -rf deploy/data/node-*/system/frontier/<id>
```


## Also
------------------------------

`deploy/examples/` is new: four catalogs worth crawling as json, and `seed-catalogs.sh` to post
them. They exist so the first thing anybody sees is not an empty page.

What delete does get right, verified end to end on the same clear-out:

- the dry run is honest -- the plan named 883 items for Rust Blog across four layers, and 883 is
  what went
- layers are genuinely separate: dropping `index,vector` on Wikinews left 67 rows and 67 pages of
  files untouched, search went to 0, and `replay --layers=index` put all 67 back and search
  returned to 67. That is the "files are always on because the other two are rebuilt from them"
  claim, demonstrated rather than asserted
- `keepLatest=1` against a catalog holding only v0 removes nothing and says so
- a version that does not exist reports all four layers with a count of zero rather than an error
- search on an empty installation answers "Nothing has finished crawling yet" rather than an empty
  result that looks like a failed query

Full build green, 567 tests in core, coverage gate met.
