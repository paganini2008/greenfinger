2026-09-03 backend
========================================

The command line rebuilt around a catalog id, plus the report table behind it.

Everything here started from one observation: `crawl` took nineteen options and saved a catalog
definition on the way past, so a typo in any of them produced a catalog nobody had asked for and a
crawl that ran with a default nobody chose. Defining a catalog and running one are now two
different things.


## Catalog and run are separate
------------------------------

`catalog-save` is the only command that asks rather than reads. Seventeen settings, one question
each, in the order somebody setting up a crawl thinks of them, every one carrying what it accepts
and what it currently says. Return keeps what is in the brackets; `cancel` at any question abandons
the whole thing and writes nothing, because half a catalog written because somebody changed their
mind at question twelve is worse than no catalog. Input that simply ends counts as a cancel too, so
a piped invocation cannot hang.

`catalog-save --id=<id>` is the update form: the same questions with the current values in the
brackets. On success it prints the id and offers to run it -- `no | crawl | update | rebuild`, with
`no` first because return should never start anything.

New classes: `Interview` (the questions, the validation, the retries), `ConsoleIO` (reading a line,
and saying whether there is a terminal at all).

`crawl` is now `--id`, `--node`, `--threads` and nothing else. So are the other verbs.


## Everything is addressed by id
------------------------------

`--catalog` is gone. Every command takes `--id`, and `catalog-list` grew an Id column so there is
somewhere to get one.

The name is unique and looking a catalog up by it worked, which is exactly the problem: a name is
editable, so a script written against one is correct right up until somebody renames a catalog, at
which point it either fails or -- worse -- finds a different catalog that has since taken the name.
`CatalogAdminService.requireById` is by id and only by id. The web api keeps its tolerant lookup;
its callers send ids already.


## No short options, and every option says what it accepts
------------------------------

The five one-letter forms are gone. There are two parsers -- the prompt uses Spring Shell's, the
one-line form uses `CommandLine` -- and a letter that meant different things in the two failed
silently: an option written under one name and read under another is ignored rather than rejected.
Two of the five were doing exactly that.

`OptionStyleTest` replaces `CommandLineShortNameTest` and fails the build on three things: an
option with a `shortName`, an option with a blank description, and an option called `--catalog`,
`--name`, `--q` or `--before`.

Renames: `--q` to `--query`, `--before` to `--version-before`. Removals: `--semantic` (text is the
default; `--image=true` is the one genuinely different question), `--config` and with it
`CrawlOptions.fromFile` (a catalog lives in the database now), `interrupt` (replaced by `pause`),
`models-list` and `models-pull` (system detail; `--offline` still works), `index-count` and
`index-list` (replaced by `index-info`, and `vector-info` beside it).

New commands: `versions --id`, `crawler-report --id [--version]`, `pause --id`, `index-info`,
`vector-info`.


## A crawl runs behind the prompt
------------------------------

A crawl used to run on the thread that typed the command, so the prompt was gone for as long as the
crawl took and the only way out was Ctrl+C -- which stops the crawl as well as the watching.

`RunningCrawls` starts it on its own thread. `crawl` shows the live view, `q` then return leaves the
view without touching the crawl, `status` brings it back, and `pause` is what stops it. On a
one-line invocation there is no prompt to go back to, so the command waits and prints the summary as
before; that difference is one field, `oneShot`.

`status` is the live view rather than a static table, and `--all=true` adds a row per node --
across a cluster the only thing that says whether one node is doing all of the work. With nothing
running it prints the catalog table it used to.

`LiveDashboard` now counts how many lines it printed instead of asking the renderer to predict it.
The block changes height while it is up -- a node joins and the per-node table grows a row -- and a
redraw that moved back by yesterday's height left a trail of half-erased tables.

The prompt is `greenfinger:>` (`GreenfingerPrompt`, replacing Spring Shell's `$>`, which in a
screenshot is indistinguishable from a shell).

`--threads` finally does something: `CrawlerEngine.setWorkThreads` overrides the configured count
for one run, threaded through new `CrawlerLauncher` overloads. It was collected and silently
dropped before.


## `--node` and the launcher
------------------------------

`--node` is read by `greenfinger-cli.sh` before the jvm starts, from anywhere on the line, and is
left in place -- `crawl` declares it too, so what you typed and what the jvm receives stay the same
thing. Typed at the prompt it says it does nothing rather than letting somebody believe they are
crawling on three nodes. The launcher's own `-n`/`-d` are gone; `--worker-dir` is what is left, read
before the command word.

Packaging: the executable jars now go to `deploy/bin/`, so `deploy/` holds the launchers, the
configuration and the data rather than 850 MB of jar beside them. Both launchers look in `bin/`
first. The configuration was already outside the jar and stays there.

**Left behind:** the previous `deploy/greenfinger.jar` and `deploy/greenfinger-api.jar` are stale
now that packaging writes to `bin/`. They are yours to remove.


## `crawler_report`
------------------------------

One row per `(catalog, version)`, holding the dashboard frozen at the moment the run ended, as json.
Written by the node that started the run and by that node only: three nodes each writing their own
idea of "the whole crawl" would be three rows disagreeing about the same number.

| Section | What is in it |
|---|---|
| `run` | action, refresh, start and end, why it stopped, what it left over |
| `dashboard` | every counter the live view was showing |
| `nodes` | the same counters per node |
| `cluster` | members, leader, channel metrics, buffer levels, split brain |
| `database` | product, version, url without its query string, rows in this version |
| `storage` | local or MinIO, where, how many files, how many bytes |
| `outputs` | the index and the vector store this version was written to |
| `settings` | `settings.json` whole |

Everything it can find out is written down, including what is empty: a missing section reads as
"nobody looked" and a zero reads as what happened. Re-running a version rewrites the row and moves
`updated_at`; `created_at` keeps saying when the version was first built. Deleting a version's `db`
layer takes its report with it.

New: `CrawlerReport` entity, `CrawlReportStore` / `JpaCrawlReportStore` / `CrawlerReportRepository`,
`CrawlReportRecorder`, `ClusterSnapshot` (with `GossipClusterSnapshot` in greenfinger-cluster).
`CrawlReportService` gained `versions()` and `stored()`. The per-run json beside the pages stays: it
is a different document, written by every node, describing that node's own share, and it survives
the database being thrown away.

Two bugs found by running it rather than by a test:

- **The node list had a phantom row.** `perNodeCounters()` keys by the short node id and
  `getMembers()` by the full uuid, so "a member that fetched nothing still gets a row" added an
  empty duplicate for every node that had in fact worked. Matched loosely now, and
  `CrawlReportRecorderTest` covers it.
- **`clusterSnapshot` would not start.** greenfinger-core's configuration is imported by the
  application rather than auto-configured, so it is processed first; a same-named bean in
  greenfinger-cluster is not an override but a duplicate definition, and the jar failed to start
  with "a bean with that name has already been defined". Renamed to `gossipClusterSnapshot` and
  marked `@Primary`, which is the shape every other override in that class already had.
  `BeanNameCollisionTest` compares the two configurations' `@Bean` method names so the next one is
  caught by the build.


## `extractor` is an enum
------------------------------

`ExtractorType`: ADAPTIVE, RESTCLIENT, HTMLUNIT, PLAYWRIGHT, SELENIUM, with the 1.x spellings
`default` and `resttemplate` still accepted for restclient. It was free text, which meant a typo was
only discovered when the crawl went to build its extractor -- after the catalog had been saved and
the run launched. Now it is refused where it is typed, with the accepted values in the message.

The column stays a string and the json stays a string, so nothing downstream changed: `Catalog`
keeps the value in `extractorValue` and exposes `getExtractorType()` under `@JsonProperty("extractor")`,
the same pattern `outputTypes` and `contentMode` already used (Hibernate infers a check constraint
for an enum-typed column and the one it generates rejects every value on H2). There is deliberately
no `String getExtractor()` beside it: two getters for one json property is something Jackson refuses
outright, and it would be a second door into the column that skipped the validation.

`CatalogDetails.getExtractor()` returns the enum now, and `DefaultWebCrawlerComponentFactory`
switches on it.

Embedded search: Lucene 9 as the default index and vector store
========================================

Later the same day. Two requests behind this: Elasticsearch here is now 9.5.2 with IK installed,
and one index per catalog rather than one for everything; and an embedded engine so that
`-o file,index,vector` needs nothing installed at all.


## One index per catalog
------------------------------

`<prefix>-<catalogId>`, holding every version of that catalog; versions are still told apart by the
`catalogVersion` field. Three things get better and one gets worse. Deleting a catalog is dropping
an index rather than a delete-by-query that only marks documents; a catalog can have its own
analyzer, which matters the moment one site is Chinese and another is not; and a search that names
its catalogs reads that many indices instead of filtering the whole corpus. What gets worse is that
a search across everything fans out over n indices -- cheap at the tens of catalogs this is for,
and the reason the setting is a prefix so `<prefix>-*` addresses the lot in one request.

From the id, never the name, for the same reason every command now takes `--id`: a name is
editable, and an index named after one is orphaned by a rename with nothing to say what it held.

`greenfinger.output.index.name` is therefore gone; `prefix` replaces it (`GF_INDEX_PREFIX`).
Existing Elasticsearch data was disposable, so there is no migration.

Elasticsearch 9.5.2 itself needed no code change -- the REST calls used here are identical across
7, 8 and 9, which is why the raw client was chosen -- beyond `listIndices` now asking for
`_cat/indices/<prefix>-*` rather than the server's whole list, and `refresh` covering the same
pattern.


## Lucene, embedded, as the default
------------------------------

Lucene 9.12.1 -- deliberately 9 rather than 10, because 9 is what Elasticsearch 8 is built on --
providing both outputs:

| Output | Default | The other option |
|---|---|---|
| `index` | Lucene, `data/.state/lucene` | Elasticsearch |
| `vector` | Lucene, `data/.state/lucene-vector` | Qdrant or Weaviate |

This is the same engine at both ends rather than a toy standing in for a real one: Lucene's HNSW is
the implementation Elasticsearch's own knn search uses. The documents are identical -- the same
fields, the same `catalogVersion` filter, the same index naming -- so moving to a server is a
`replay`, not a migration.

New: `IndexAdmin` (the interface both index engines implement), `LuceneIndexes`, `LuceneFields`,
`LuceneAnalyzers`, `LuceneOutputChannel`, `LuceneSearcher`, `LuceneIndexAdmin`, `LinkDensityScore`,
`LuceneVectorStore`. `OutputFactory` grew `getSearcher()`, `getIndexAdmin()` and a provider switch;
`DeletionService`, `QueryCommands` and `SearchApiController` stopped constructing Elasticsearch
classes directly and go through it. greenfinger-cli therefore gets all of it for free, which was
the point of routing it through the factory rather than through a second `if`.

The searcher matches the Elasticsearch one clause for clause: title above body, detail pages above
listings by link density (a `DoubleValuesSource` where Elasticsearch has a script), passages marked
with `<em>`, and the same 10,000 result ceiling with the same cursor past it. Two details worth
recording:

- **Several catalogs are read through one `MultiReader`**, not searched separately and merged.
  BM25 scores from term statistics, and gathering them per index would score a word that is rare
  overall but common in one small catalog as though it were common everywhere.
- **The cursor carries `[score, id]` and sets the Lucene document number to the highest legal
  one.** Lucene only consults the document number when a hit ties with the cursor on every sort
  field, and the last sort field is the document's unique id -- so the only document that can tie
  is the one the cursor names, and the highest value skips exactly that one. Carrying the real
  document number would have worked until the first merge renumbered it.

**The analyzer stays `standard`.** IK being installed does not make this a Chinese crawler; English
is the expected case and `standard` is right for it. `smartcn` (a real segmenter, the embedded
counterpart of IK) and `cjk` (bigrams, no dictionary) are there for the catalogs that want them.
The three IK spellings map to `smartcn`, because that is what somebody moving a configuration
across will have written. It is one setting per node today; one index per catalog means it could be
one per catalog, which is a column and an interview question that do not exist yet.


## Across a cluster: replicated, like the blob store
------------------------------

An embedded index is one copy per node, and a url is dispatched to exactly one node, so most of the
corpus would be missing from every node's answer. Documents and vectors are copied to every node as
they are written, on a channel of their own (`greenfinger.search`): `ReplicatedIndexChannel` and
`ReplicatedVectorStore`, in the shape `ReplicatedBlobStore` already had.

The document travels whole rather than as a pointer to a row that is also being replicated: the
channels are independent and nothing orders them against each other, and an index that silently
missed a page whose row landed a moment later would be worse than the bandwidth. The vectors travel
as raw floats -- json would be four times the bytes and lose the last digit of each -- because
re-embedding on three nodes is three times the model's work.

It costs the extracted text once per node, on top of the copy already going over the blob channel.
A cluster that crawls seriously wants a real Elasticsearch; the startup report says so.


## `output` is now blob, index, vector
------------------------------

`output/local/` and `output/elasticsearch/` are gone: `FileOutputChannel` moved to `output/blob/`,
the three Elasticsearch classes and the Lucene index classes to `output/index/`, and
`LuceneVectorStore` to `output/vector/`. Three subpackages, named after what they produce rather
than after the product that happens to serve them.


## created_at and updated_at everywhere
------------------------------

Every table carries both, spelled the same way:

| Table | Was | Now |
|---|---|---|
| `crawler_catalog` | `last_modified` | `created_at`, `updated_at` (`last_indexed` stays: it is a fact about the data, not the row) |
| `crawler_resource` | `create_time` | `created_at`, `updated_at` |
| `crawler_image` | `create_time` | `created_at`, `updated_at` |
| `crawler_resource_image` | `create_time` | `created_at`, `updated_at` |
| `crawler_report` | — | already had them |

`crawler_resource.last_modified` was not a row timestamp at all -- it is the site's
`Last-Modified` header, offered back on the next merge so the server can answer 304 -- and a column
of that name sitting next to `updated_at` is a question nobody should have to ask twice. Renamed to
`http_last_modified`. The search documents keep their `createTime` field name; that is a document
field, not a column, and nothing outside the database reads it by the other name.

`ReplicatedCatalogStore` compares catalogs with the write stamps removed, and now removes both.


## Two bugs found by running it, not by a test
------------------------------

- **The vector store was used before anything opened it.** `VectorOutputChannel.open` calls
  `ensureCollection`, and every caller reasonably assumed constructing a store was enough --
  because until now one was an http client. With Lucene, `afterPropertiesSet` is what opens the
  directory, so the whole vector output was skipped for the run with a warning nobody would read
  until afterwards. It opens on first use now.
- **`vector-info` counted a collection that has never existed.** The width is appended when the
  vectors are written -- `greenfinger_text_384` -- so counting the configured name reports zero and
  reads exactly like "nothing has been embedded". It asks by prefix now, which is what
  `collectionsMatching` was there for.

Also fixed while the tests were moving: the search fixtures had only ever crawled the seed page,
because the default path pattern is built from the host and does not match a bare ip and port. The
Elasticsearch stub returned canned hits regardless, so nothing noticed until the search became
real.

## `InMemoryResourceRecordStore` is gone
------------------------------

`CrawlerEngineTest` now runs against the real record store on H2, like every other integration test
here, and the hand written stand-in is deleted.

It was a second implementation of `ResourceRecordStore`'s semantics -- id derivation, upsert by id,
image references -- that had to be edited in step with the real one and quietly went wrong when it
was not. Twice in one day: once for `setHttpLastModified` and once for `setCreatedAt`. The engine's
job is to write rows, and letting it write them into a database is both more honest and one fewer
thing to keep in step. Cost is about six seconds of context start for that class; the assertions
are unchanged, all ten still pass.


Three delete semantics, `face`, and the launcher's own options
========================================

## `delete`: by version, every version, the catalog
------------------------------

`deleteByCatalog` existed on `IndexAdmin` and had never been called: `--all` looped over versions
issuing one delete-by-query each and left the emptied index standing. The three are now three
operations rather than one with three spellings, and every store implements all three.

| Scope | CLI | The index | Everything else |
|---|---|---|---|
| by version | `--version=<n>`, `--keep-latest=<n>` | delete by query on `catalogVersion` | by version |
| every version | `--all=true` | delete by query on `catalogId`; the index survives, emptied | one statement for the catalog |
| the catalog | `--purge=true` | **the index is dropped** | the same statement |

The index is the only store where the last two differ, because it is the only one that belongs to a
single catalog. A vector collection is shared -- its name carries the width of the vectors, not the
catalog -- so is a table, and a directory is emptied by removing its contents.

Why it matters: emptying is a marked deletion whose space returns when segments merge; dropping is
immediate, complete, has nothing to merge, and takes with it any documents belonging to versions
nothing else remembers.

Added to make it possible: `IndexAdmin.countByCatalog` / `deleteAllVersions` (both engines),
`VectorStore.countByCatalog` / `deleteByCatalog` (Lucene, Qdrant, Weaviate),
`ResourceRecordStore.deleteByCatalog` and `CrawlReportStore.deleteByCatalog` (with the repository
derived queries behind them), and `ReplicatedVectorStore` / `ReplicatedRecordStore` ops so a
whole-catalog delete on one node reaches the others. `DeletionService` grew `cleanCatalog` and
`deleteCatalog` beside `delete`; a wholesale delete issues **one statement per layer**, counting per
version first so the report is still read version by version.

`--version-before` is gone. `--keep-latest=<n>` keeps the newest n and removes the rest, which is
the same question asked the way somebody actually asks it. The web api lost `before` and gained
`purge` to match.

`--force`, since it came up: it allows removing the version search is currently serving, and
nothing else. The other refusal -- a version being crawled right now -- is not overridable.


## `face`, and a shell that had never once started
------------------------------

`greenfinger-cli.sh face` opens a session: one jvm, the `greenfinger:>` prompt, every command
available inside it. Anything else is one-shot.

Typing it found that **the interactive shell had never worked at all**. Spring Shell starts it from
an `ApplicationRunner` bean declared `@ConditionalOnMissingBean` on `ApplicationRunner` -- and
`OneShotCommandRunner` is one, so it backed off and the shell was never created. A bare
`greenfinger-cli.sh` booted for twenty seconds, ran nothing and exited. `OneShotCommandRunner` opens
the prompt itself now.

The prompt then still came out as `$>`. Declaring a `ConsoleInputProvider` bean was not enough --
the bean was created and the runner was built with the autoconfiguration's own anyway -- so the
runner is assembled explicitly from `GreenfingerPrompt`, a `CommandParser` and a `CommandRegistry`.
Ours by construction rather than by bean resolution.

Worth knowing for next time: `mvn package` without `clean` silently skipped recompiling an edited
file twice during this, which sent me chasing a bug in code that was not in the jar. A clean build
is what settled it.

| Option | Default | What it does |
|---|---|---|
| `--data-store` | `deploy/data` | One directory for everything this node writes |
| `--cluster` | `default` | Which cluster to join |

The data directory: system and user
========================================

The question was whether the data directory is laid out the way it was designed to be. It nearly
was; five things differed, and four of them are now changed.


## Two halves, and what each one costs to lose
------------------------------

`--data-store` was already one directory with everything under it. What it was not was **split by
what the data is for**. It now is:

```
deploy/data/                                 the default --data-store
  system/                                    the crawler's working state
    greenfinger.mv.db                        H2, when no database server was configured
    frontier/{catalogId}/v{n}/               RocksDB: the urls still to visit
    dedup/url/{catalogId}/v{n}/              RocksDB: what has been seen
    dedup/content/                           RocksDB: content fingerprints
  user/                                      what was crawled
    assets/{catalogId}/v{n}/                 settings.json, reports/, pages/, images/
    index/{prefix}-{catalogId}/              embedded Lucene, one index per catalog
    vector/{collection}_{dimensions}/        embedded Lucene, one per embedding width
```

The line between them is one sentence: **delete `system/` and a search still works.** It costs a
resume and a re-crawl of whatever was in flight, and nothing else. `user/` is what a query reads,
and it is the half worth backing up. That is why the crawl's working state is an advanced setting
and the crawled data is not.

Two environment variables carry it, and they are new names for the two that existed:

| Was | Is | Holds |
|---|---|---|
| `GF_STATE_DIR` | `GF_SYSTEM_DATA_DIR` | frontier, dedup, the H2 or SQLite file |
| `GF_DATA_DIR` | `GF_USER_DATA_DIR` | assets, index, vector |
| -- | `GF_DATA_STORE` | the parent of both; what `--data-store` sets |

`index/` and `vector/` moved out of `.state` in the process. They had been sitting with the
RocksDB stores, which said they were disposable; they are not -- rebuilding an index means
replaying every page through an embedding model.


## These directories describe the local stores, and nothing else
------------------------------

A node whose assets go to MinIO, whose index is Elasticsearch and whose vectors are in Qdrant has
no `user/` directory at all. The launcher creates `system/` and stops there: that half is always
local, because the frontier and the dedup filters are RocksDB whatever else is configured. The
three directories under `user/` are created by whoever writes into them, so the layout above is
what a local, zero-install node looks like -- not a shape imposed on every deployment.


## Addressed by id, like everything else
------------------------------

`FileLayout` built its paths from the catalog's **name**. Now it builds them from the id:

```
before   deploy/data/books.toscrape.com/v0/pages/ab/cd/{id}.html
after    deploy/data/user/assets/01a064a8-.../v0/pages/ab/cd/{id}.html
```

The index directories were already `{prefix}-{catalogId}`, so the two halves disagreed about what
a catalog is called. They agree now, and renaming a catalog moves nothing on disk. It also closes
the collision `safeName` could produce: two catalogs whose names differ only in a character the
file system will not take were sharing a directory.

Vectors are deliberately **not** split per catalog. A collection is one embedding width
(`greenfinger_text_384`), and which catalog and which version a point belongs to is a field on it,
filtered at query time -- which is how Qdrant and Weaviate are addressed too, so the embedded
store and the servers behave identically.


## `file` stays `file`
------------------------------

The directory is `assets/`. The output type is still `file`, `--layers=file` still means the same
thing, and `greenfinger.output.file.*` is still the configuration key. Only the directory was
renamed; an enum value that reaches the database, the api and every script is not worth churning
to match a folder name.


## Two launchers
------------------------------

`greenfinger-cli.sh` runs one command and exits. `greenfinger-face.sh` opens the `greenfinger:>`
prompt. They are the same implementation behind two entry points -- `face.sh` sets
`GREENFINGER_FACE=1` and hands over -- so the jar, the configuration, the `.env` file, the data
store and the extra nodes are found by exactly the same code whichever was typed.

Two consequences, both intended:

- **`./greenfinger-cli.sh` with nothing on the line now prints `help`** instead of opening a
  prompt. That was on the open list from this morning; the prompt having its own launcher answers
  it.
- **`face` on the line still works** and means the same thing, so nothing typed before breaks.

`greenfinger-api.sh` gained `--data-store` and `--cluster` with the same meaning and the same
default, so the server and the prompt started side by side read and write one data directory
rather than two.

The default `--data-store` is now `data/` **beside the launcher** rather than `./data`. Where you
happened to `cd` to before typing the command no longer decides where a crawl is written.

## Deleting a version takes its RocksDB with it
------------------------------

`delete --version=0` removed the rows, the files, the index documents and the vectors, and left
`system/frontier/{catalogId}/v0` and both dedup filters exactly where they were. Every version
ever crawled left three directories that nothing would open again, and a `resume` that found the
frontier of a deleted version would have started fetching urls whose rows are gone.

They now go with the **`db`** layer, not as a layer of their own: those stores exist to answer
"have I fetched this already", and the rows are what that question is about. `--layers=db` clears
them, `--layers=file` does not, and a dry run reports the bytes without removing anything. A
whole-catalog delete takes the catalog's whole tree in one go rather than a version at a time.

The byte column of the `db` row now says how much came back from the system half; it was always
zero before.


## `--layers` never accepted the separator it documents
------------------------------

Every piece of help and documentation says the layers are joined with `+`. Both parsers split on
`[,;\s]+`. So `--layers=file+index+vector` -- copied from the help -- failed with
`Unknown OutputType: file+index+vector`, and only the comma form worked. Found by running the
replay check below. `OutputType` and `DeleteLayer` now take `+` as well.


## The jars carry their version
------------------------------

`deploy/bin/greenfinger-api-2.0.0-SNAPSHOT.jar` and `greenfinger-cli-2.0.0-SNAPSHOT.jar`. What a
node is running can be read off the file rather than out of a manifest. The launchers pick the
newest match and still accept the old unversioned name; `Dockerfile` copies by pattern and renames
on the way in, so the entry point needs no wildcard.

Two things were found on the way: `Dockerfile` was still copying `deploy/greenfinger-api.jar` --
the stale copy at the top of `deploy/`, not the one packaging writes to `bin/` -- so every image
built since the jars moved was a release behind. And `run-docker.sh stop` used `mapfile`, which is
bash 4; macOS ships 3.2, where that whole branch was a "command not found" and no container was
ever stopped.

## Deleting the whole user data directory, and replaying it back
------------------------------

The question the two halves exist to answer, asked directly: **`rm -rf data/user`, then what?**

```
rm -rf data/user                                    18 files gone
search --query "green finches"                      No matches
replay --id=<id> --layers=file+index+vector         Replayed 3 page(s) of v0
                                                    Files: 3 written, 0 already there,
                                                           0 unreachable, 0 changed since the crawl
search --query "green finches"                      1 match, the right page
```

Everything came back: the three pages, their extracted text, `settings.json`, the Lucene index and
the vectors. One command does all three layers because a single pass writes the files and the two
later layers read them straight back.

The one thing that does not come back is `reports/` -- the account of a run that happened. Replay
cannot invent it, and the copy in `crawler_report` is still there. That is the right answer, not a
gap.

The order matters and the command enforces it: the index and the vectors are built from the text
the file layer writes, so `--layers=index` alone against an empty `user/` has nothing to read.
And it only works while the site is still up: the pages exist in exactly two places, the original
site and `assets/`.


## Three nodes in containers, sharing Elasticsearch and Qdrant
------------------------------

`./run-docker.sh -n 3`, H2 per node, the index in Elasticsearch 9.5.2 and the vectors in Qdrant,
both on this machine and reached as `host.docker.internal`. The crawl was started on node 1
through the api.

| Checked | Result |
|---|---|
| the three nodes joined | one cluster, node 1 leader |
| pages, per node | 10 files each -- a complete copy on every node, which is what replication is for |
| Elasticsearch | one index, `greenfinger-{catalogId}`, 3 documents |
| Qdrant | one collection, `greenfinger_text_384`, 3 points |
| the catalog definition | on all three nodes |
| search from node 1 | 1 match |
| search from nodes 2 and 3 | **refused** -- see below |

`run-docker.sh` needed three fixes before this ran at all, all noted above: the image was built
from the stale jar at the top of `deploy/`, `stop` used `mapfile`, and there was no way to hand a
node a database or a search server without editing the committed configuration. It now passes
through the `GF_*` variables that name a store.

1200m per container is not enough once the embedding model is loaded -- node 2 was OOM killed
(exit 137) part way through. 2600m was fine. The default in the script is still 1200m, which is
right for a crawl that is not embedding anything and wrong for one that is.

**A node that is not the leader will not serve a search.** All three have the catalog and all
three can reach the shared index, but `search_version` is published by the leader into its own
database, and with H2 that database is per node: nodes 2 and 3 answer "Nothing has finished
crawling yet" while node 1 answers the query. In a three node cluster that is two thirds of the
capacity refusing to work. Same root as the `rebuild --node=2` note from this morning: what the
leader publishes does not reach the others.


## The same three nodes on MySQL
------------------------------

`GF_PROFILE=prod` and `GF_DB_URL=jdbc:mysql://host.docker.internal:3306/demo`, everything else
unchanged. `ClusterReplication` reported it correctly without being told:

```
Replication: dedup on, records off (MYSQL is shared), blobs on (local directory per node),
             search off (a shared search server)
```

Three pages, 10 files on each node, 3 documents in Elasticsearch, 3 points in Qdrant -- and
**all three nodes answered the search**, where on H2 only the leader did. That confirms the
diagnosis above rather than fixing it: `search_version` is a column, so a shared database makes
every node see the leader's publish for free. On a per-node database it has to be replicated, and
it is not.

So the H2 cluster is the configuration where this bites, and it is also the zero-install default.
Worth fixing before anybody runs three nodes without a database server.


## Found while testing, not chased
------------------------------

**A leader that is not taking part in a crawl never declares it finished.** `CrawlCluster.supervise`
loops over `coordinators.keySet()` -- the crawls *this* node is in -- and returns immediately
unless this node is leader. Start `greenfinger-api.sh`, let it win the election, then run
`catalog-crawl` from the command line: the crawl fetches everything, the counters meet, and
nothing announces it. The engine sits in `ThreadUtils.sleep` waiting for `isCrawlFinished()`, and
the 5 minute stale timeout does not save it either, because that check is inside the same
leader-only branch.

Reproduced twice today, by accident, while testing the directory change with the server running.
It is not new and nothing about today's work caused it. The fix is presumably that a leader
supervises every crawl the cluster knows about rather than only its own, which means the set of
running crawls has to be cluster state rather than a local map -- not a small change, and not one
to make while testing something else.


greenfinger-shell, and the cluster the browser talks to
========================================


## The module is greenfinger-shell
------------------------------

`greenfinger-cli` -> `greenfinger-shell`: the maven module, the artifact, the package
(`com.github.greenfinger.cli` -> `.shell`), the main class, the jar
(`greenfinger-shell-2.0.0-SNAPSHOT.jar`) and the worker property. The launchers keep their names --
`greenfinger-cli.sh` is still the one-shot face and `greenfinger-face.sh` still the prompt -- and
the launcher still finds a jar under the old name, so an existing install keeps working.


## `--node` inside a session actually forks now
------------------------------

It used to print "`--node` is read by greenfinger-cli.sh before this process starts, so it does
nothing here". That was true and useless: the session is a node, and asking it for three should
give three.

`catalog-crawl --id=<id> --node=3` at the prompt now forks **two** workers, because the session is
node 1 -- and, having started first and taken the cluster port, it is the leader. Confirmed in
spreader's own code rather than assumed: `MemberList.pickLeader` walks the members sorted by
`Node.compareTo` (priority, then start time, then id) and returns the first one **holding the
cluster port**. So the prompt leads while it is up, and when it leaves, the port is released and
whichever worker takes it leads instead -- there is a short window with no leader, which is the
"集群暂时无主" line in the log.

The forking is done by running the launcher, not by assembling a command line in Java:

```
greenfinger-cli.sh --as-worker      with GREENFINGER_WORKER_DIR set
```

`--as-worker` is new and is not for typing. It calls the same `worker_env` the launcher uses for
its own workers, so a worker forked by the prompt and one forked by the launcher are the same
process with the same data directory, the same database rule and the same cluster. Writing that
rule again in Java would have been two implementations of it, and they would have drifted.

The workers stop when the crawl that asked for them finishes, so a session that crawls twice with
`--node=3` runs three nodes twice rather than three and then five. Detaching from the live view
with `q` leaves them alone -- the crawl is still going and still wants them. `LocalNodesTest`
covers the contract with a stand-in launcher.

Running one for real turned up something that had been there since workers existed: a worker was
**opening a prompt**. `OneShotCommandRunner` sees no command on the line and opens one, and its
guard for this case was "the shell beans are missing", which they are not. Harmless -- stdin is a
redirect, the prompt reads one end-of-file and closes, and `WorkerNodeRunner` is what keeps the
process alive either way -- but it was a prompt on a process nobody is typing at. It now checks
`greenfinger.shell.worker` and returns.


## `spring.spreader.ip-addresses`, and the address a node hands out
------------------------------

It was configured (`GF_CLUSTER_HOSTS`, default `127.0.0.1`) but only `run-docker.sh` ever set it.
The three launchers now take `--cluster-hosts`, and naming hosts also **unpins the advertised
address**: `advertise-host` is fixed at `127.0.0.1` in the configuration so that several processes
on one machine do not advertise an interface none of them can reach, and that default is exactly
wrong the moment another machine has to dial this one. That was the cross-machine defect raised
twice and never answered; it is answered now.

`run-local.sh` takes it as `-H`, and its header no longer teaches the form that could not work:
it used to say `GF_CLUSTER_HOSTS=<A>,<B> ./run-local.sh` on machine B, which is the exact
invocation that leaves B advertising a loopback address A cannot reach.

`run-docker.sh` goes further and gives the network a fixed subnet (`172.28.0.0/16`) with a fixed
address per node. Container names would have worked -- docker resolves them -- but then the thing
this setup exists to check, that nodes find each other by address the way they would on real hosts,
would be answered by docker instead of by spreader.


## The front end is its own container
------------------------------

It was baked into the api image and served by each node, so a browser talked to one node rather
than to the cluster. `run-docker.sh` now also starts `greenfinger-web`: nginx, the Angular build,
and the api proxied to every node with `least_conn` (a crawl request holds a node for as long as
the crawl runs, and round robin would keep handing work to a busy one). One address --
`http://localhost:50079` -- in front of however many nodes are running. `--no-web` skips it.

The nodes still serve the app themselves. That is what makes one process a complete installation,
and it is what `run-local.sh` relies on.

**Signing in through it failed twice, for two different reasons, and both looked like a wrong
password in the browser.**

First, 403 `Invalid CORS request`. The page is loaded from the front end container, so the browser
sends `Origin: http://localhost:50079`, and the node it is proxied to had only been told about
`http://localhost:4200`. curl never sent an Origin, which is why every check up to that point had
passed. `run-docker.sh` now tells the nodes the front end's real origin (the port is an argument,
so it cannot be a fixed default), and the configuration lists it as a fallback.

Then, with the sign-in working, the next request came back `Sign in first`. **A token lives in the
memory of the node that issued it** -- `TokenStore` is a `ConcurrentHashMap` per node -- so a
request balanced onto a different node is not authenticated. The sign-in landed on node 3 and the
request after it on node 1.

nginx cannot fix that. `ip_hash` looks like the answer and is not: inside docker every browser
request arrives from the same gateway address, so it would pin the whole world to one node.
Hashing the token would pin consistently but not necessarily to the node that issued it.

So the upstream is **failover, not balancing**: node 1 takes the traffic and the others stand by,
and a node that stops answering is passed over. Whoever was signed in signs in again -- the honest
cost of the token being where it is. Spreading requests across the cluster needs the token to be
verifiable anywhere, which is a decision about the api and is in the open list below.

The `.dockerignore` is new too: the build context was the whole `deploy/` directory, data store
and 880 MB of jars included, uploaded to the daemon before anything was built.

Open, for next time
========================================

Nothing here is broken work in progress; it is the list of decisions not taken and things noticed
in passing. Ordered by how much they would cost somebody who did not know about them.


## Waiting on a decision
------------------------------

- **A sign-in token is only valid on the node that issued it.** That is what makes the front end
  container failover rather than load balancing, and it is the one thing stopping three nodes from
  serving three times the requests. Two ways out: sign the token so any node can verify it without
  holding it, or replicate `TokenStore` the way the catalogs are replicated. The first is standard
  and has no window where a fresh token has not arrived yet; the second matches how everything
  else in this cluster is shared. Not a decision to make while testing something else.

- **`update` / `rebuild` / `resume` / `pause` keep their bare names.** `crawl` became
  `catalog-crawl`; these four act on a catalog too, so either they follow or the prefix means
  nothing. Not renamed because it was not asked for.
- **`catalog-show` still prints a "Last run" section.** `crawler-report` does that job properly
  now. Suggested: drop the section, keep the command -- it is the only read-only view of all
  twenty settings.
- **A per-catalog analyzer is possible now** that each catalog has its own index, and is what a
  machine crawling one English site and one Chinese site wants. It needs a catalog column and an
  interview question; neither exists.


## Known and not chased
------------------------------

- **`rebuild` does not move `search_version`.** Seen this morning on `--node=2` and again this
  evening on three containers: after a rebuild every node agrees on `index=v1` and every node
  still says `search=v0`. The versions being consistent across the cluster is what narrows it --
  the publish is not happening, rather than happening and failing to replicate. `CrawlerLauncher`
  publishes on `completed && publisher`; which of the two is false was not established.
- **`--url` and `--start-url` resolving to the same page can save one url twice** and hit the
  resource primary key. The crawl continues and the pages are right; it is two threads racing the
  dedup gate on the seed.
- **The delete page has still not been clicked through.** The app was served, signed into and
  searched through the front end container today, and the build in `deploy/static` is from
  2026-09-02 -- before `before` was dropped and `purge` added. Loading it proves nothing about
  that dialog.
