## 本次对齐推翻/修正了哪些既有设计

这一轮跟 Fred 逐条对齐，改动面比预想大，下面这些是**跟 8-29 版本设计不一致**的地方，改代码前务必以本文为准：

1. **数据库从可选变必选**。`application.yml` 里 exclude 掉 DataSourceAutoConfiguration 的做法作废，默认 h2 文件库。`greenfinger.record.enabled`、`Catalog.recordEnabled`、`--record` 全部删除。
2. **三条输出从"三选一"变"可叠加"**，且 `file` 恒为必选。`OutputType` 单值枚举 → `output_types` 多值列。
3. **数据库只存 metadata**：`crawler_resource` 删掉 `html` 和 `content_text` 两个大字段，改存 `html_file_path` / `html_content_file_path`；图片路径存 `crawler_image.image_file_path`（`blob_uri` 列删除）。
4. **图片拆成两张表**：`crawler_image`（实体，按 catalog+version 内的 content_hash 去重）+ `crawler_resource_image`（多对多关系，承载 alt/title/context）。
5. **id 体系全换**：`IdGenerator` / `SnowflakeIdGenerator` 删除，改用 UUID。catalog 用 v7，resource / image / resource_image 用 v5（确定性）。全部 `char(36)` 文本存储，四层字面一致。
6. **四层全部多版本并存**（db + file/minio + index + vector），`rebuild` 只做 version+1，不删任何数据。
7. **新增删除 API**，`--layers db/file/index/vector/all`，删除顺序是写入顺序的逆序。
8. **新增 `search_version`**，修掉 1.x "rebuild 期间搜索空窗"的缺陷。
9. **新增 `max_versions`**（默认 10，默认开启自动 prune）。
10. **登录态相关代码全部删除**（`CatalogCredential`、`StatefulExtractor`、`WebClientHolder`、`Cookie` 等 7 个文件）。
11. **`core.util` 包改名 `core.utils`**，`BeanLifeCycleUtils` 从顶层包移入。
12. **embedding 换成本地模型优先**：默认 multilingual-e5-small + SigLIP 2，`imageToVector` 改为 default 方法抛 UnsupportedOperationException。`HashingEmbeddingClient` 删除。

## 更正：之前报的 RocksDB "bug" 不成立

我一度判断 `RocksDbUrlPathFilter` / `RocksDbCrawlFrontier` 没有按 `catalogId + version` 隔离，依据是它们的构造函数只收一个 `directory`。**这个判断是错的**——调用方 `DefaultWebCrawlerComponentFactory.scoped()` 早就把目录拼成了 `{base}/{catalogId}/v{version}`，与 1.x 的 `f(catalogId, version)` 完全一致。

设计文档第 10 节已改写：不再是"待修缺陷"，而是"已经是对的，勿动"，并记下它是 rebuild 能重爬相同 URL 的前提。

## 新增：爬取边界是硬约束

Fred 明确要求"绝不能从 www.a.com 跑到 www.b.com"。新增两个**不可配置、不可移除**的 acceptor，排在所有其他 acceptor 之前：

- `DomainScopeUrlPathAcceptor`（order = `Integer.MIN_VALUE`）：可注册域必须与 `catalog.url` 一致，兄弟子域算同站
- `StartUrlPrefixUrlPathAcceptor`（order = `MIN_VALUE + 1`）：URL 必须以 `start_url` 为前缀；`start_url` 为空时回退 `url`

连带确认了 `start_url` 的语义：它既是种子，又是前缀约束（`/a` → `/a/b`、`/a/c` 在范围内）。**默认行为因此变成单站点**——`start_url` 默认等于 `url`。要一个 catalog 覆盖多个兄弟子域，得把 `url` 设成共同上级域并显式放宽 `path_pattern`。这与 8-29 那版 toscrape 演示数据的行为不同，注意。

## 从 1.x 代码里核实的事实（避免下次重复考古）

- `WebCrawlerService.rebuild()` = `cleanCatalog(id, false)`（删 DB resource + 删 ES 全部版本）→ version+1 → crawl。**1.x 从不累积多版本**，2.0 在这一点上有意偏离。
- `update` 在 1.x 只被 `WebCrawlerJob.java:89`（自动任务）调用，起点是 `getLatestReferencePath()`，version 不变。
- 搜索：`ElasticsearchResourceIndexManager.java:212-213`，version 为 null 时取 `maximumVersionOfCatalogIndex(cat)`。
- ES 文档 id：`indexedResource.setId(resource.getId())` —— **1.x 的 DB 和 ES 已经是同一个 id 了**。
- 幂等靠唯一约束 `unique (catalog_id, cat, version, title, url)`，撞了就 `catch (DuplicateKeyException)` 打条 warn 丢弃（`WebCrawlerHandler.java:203/336`）——所以**1.x 的重爬其实是"跳过"，不是"更新"**。
- 那条唯一约束建在 `url varchar(1000)` 上，只因为 1.x 只跑 PostgreSQL。搬到 MySQL 会直接建表失败（InnoDB 索引键 3072 字节上限，utf8mb4 下单列 768 字符）。2.0 因此引入 `url_hash char(64)`。
- doodler 的 `IdGenerator` 实现在 `doodler-common-id`，该 jar 不在本地 m2 仓库，**读不到实现**，只知道接口是 `long getNextId()`。

## 评审后期又敲定的几条（比初稿有变化，注意）

- **ES 回到单索引** `webcrawler_resource`（对齐 1.x），放弃"一版一索引 + 别名"的方案。版本隔离改用 `catalogVersion` keyword 字段（`"<catalogId>:<version>"`），ES 与向量库 payload 两边写法对称。删版本因此只能 `delete_by_query`（标记删除），给了个默认关闭的 `--forcemerge` 开关。
- **目录去掉 host 层**：`{catalog}/v{version}/{settings.json, manifest.jsonl, pages/, images/}`。跟 8-29 版设计不同，同一 catalog 下各站点共用 `pages/` 与 `images/`。
- **`settings.json` 移进版本目录**，删版本时配置一起走。
- **不为图片加计数类型**，`INDEXED_RESOURCE_COUNT` 的 URL 维度够用，图片不参与 `maxFetchSize` 限流。
- **图片两个开关**：`image_enabled`（抓不抓图）+ `downstream_content`（`text_image` / `text`，index 与 vector 要不要图片）。CLI 是 `--images` 与 `--content text+image|text`。
- **`cat` 是用户自定义标签，系统不维护**。1.x 的 `maximumVersionOfCatalogIndex(cat)` 按 cat 取最大版本是缺陷（同 cat 下落后的 catalog 数据被搜索忽略），2.0 版本严格 per-catalog。
- **replay 从数据库覆盖重建 index / vector**，`manifest.jsonl` 降级为"连库都丢了"的灾难恢复。因为 id 是 v5 确定性生成，覆盖写天然幂等。
- **单并发**：`Semaphore(1)` 保持不变，全进程一次只跑一个 catalog。
- **`running_state`** 沿用 1.x 的 `crawl / update / rebuild / none`，`resume` 归入 `update`。
- **`resume` 与 `update` 是同一个语义**，起点按 frontier → 最近爬取位置 → `start_url` 自动解析。

## 实测中发现并修掉的真问题（下次改动前必读）

1. **`search_version` 不推进**：因 `maxFetchSize` 停止的爬取被当成未完成，搜索永远查不到东西。判据改为 `isFullyCrawled() || interruptionReason 非空` —— 配置的限流是正常结束，只有外部中断才不发布。
2. **`linkCount` 恒为 0**：`CrawlerEngine` 只跟随链接、没写回 `CrawledPage`。排序信号形同虚设。
3. **图片并发主键冲突**：同一张图被多线程同时插入。**H2 只 warn，PostgreSQL 会让整个事务 aborted**，同事务内 catch 后回读同样失败。必须 `TransactionTemplate` + `REQUIRES_NEW`，且**重试要另开事务**。注解 `@Transactional` 在同 bean 自调用时不生效，所以没用注解。
4. **Weaviate 查询字段必须在 schema 里**：payload 有而 class 没有的字段会让 **GraphQL 整条查询报错**，检索返回空而不是报错。schema 与 payload 现在从同一份常量生成。
5. **旧库升不上去**：`url_hash` 是 NOT NULL，`ddl-auto=update` 无法在有数据的旧表上加列。2.0 是重写，按 Fred 的意思老数据由他清理。
6. **Spring Shell 4 用方法名做 bean 名**：`CatalogCommands.delete` 与 `CrawlCommands.delete` 撞车导致启动失败，前者已改名 `deleteCatalog`（命令名 `catalog-delete` 不变）。

## 新增：爬取边界是硬约束

`DomainScopeUrlPathAcceptor`（可注册域）+ `StartUrlPrefixUrlPathAcceptor`（`start_url` 前缀），**不可配置、不可移除**，排在所有 acceptor 之前。`start_url` 为空回退 `url`，因此默认是单站点。

## 新增：搜索排序与深分页

- **详情页优先**：用 Boilerpipe 的链接密度（锚文本 / 总文本）。ES 走 `function_score`，向量库没有它，所以 `VectorSearcher` 过量取回后客户端重排 + 按 resourceId 去重。
- **深分页**：`from+size` 超 10000 被 ES 拒绝，改用 `search_after` 游标，排序 `[_score desc, id asc]`（`id` 是 `_id` 的字段镜像，直接排 `_id` 需要 fielddata）。

## 收尾追加的两项主流能力

**正文抽取**（`ContentExtractor`）：Boilerpipe/Readability 思路的块级打分，剥掉导航页脚。实测详情页 1573 → 1398 字符，面包屑和站点标语被去掉。**中途发现并修掉一个 CJK 偏见**：阈值按字符数算等于按英文算，中文正文全被判太短而退回整页；现在 CJK 按 4 倍计权。

**sitemap 种子**（`SitemapSeeder`）：robots.txt 的 `Sitemap:` → `/sitemap.xml` → `--sitemap-url`，用 crawler-commons 的 `SiteMapParser`，支持 index 递归。URL 照样过全部 acceptor 闸门。

**URL 归一化改两层**：实测对比后确认自己那套漏了 `/a/./b/../c`、`/%7Euser/`、`//double//slash` 三类 RFC 3986 折叠，而 crawler-commons 又不丢跟踪参数、不去尾斜杠。现在先跑它的语法归一，再叠我们的语义归一。

## 收尾追加：`update --refresh` 合并

普通 `update` 看不见已有页面的内容变化，`--refresh` 把它补成真正的 merge：绕过 URL 过滤器重访已知页面，按该 URL 自己的历史 `content_hash` 比对——相同则四层一字节不写，不同则四层覆盖写，没有则新增。

**覆盖而非新增，靠的是 UUID v5**：同一 URL 在同一 version 下 `resource_id` 恒定，所以 DB 主键、文件路径、ES `_id`、向量 point id 全不变。换 v7 这条路不成立。

**限流保护**（Fred 提出）：被 `maxFetchSize` 截断的 merge 比报错更糟——走到的更新了，没走到的悄悄留旧内容，且无记录可查。所以开始前查"已存记录数 ≥ maxFetchSize 就拒绝"，结束后查"因限流停止就抛异常"。普通 update 不受此约束。

实测：books.toscrape 完整爬完后 refresh，`Pages saved = 0`、版本仍 v0；限额不足时正确拒绝并提示应调到 1195。

### JS 渲染按需判断（`--extractor adaptive`）
`RenderingDetector` + `AdaptiveExtractor`：纯 HTTP 先抓，判断"像不像没渲染"，像才用浏览器重抓。三个信号——空的框架挂载点（`#root`/`#app`/`#__next`/`ng-app` 等）、hydration 标记（`__NEXT_DATA__` 等）、noscript 提示、脚本多而无正文。

**浏览器按需启动**：静态站点全程一个浏览器都不开。**三种引擎都能当回退目标**，由 `GF_ADAPTIVE_BROWSER` 指定；配置的引擎不在 classpath 时按 `selenium → htmlunit → playwright` 顺序回退（Selenium 优先，因为它驱动机器上已有的浏览器）。

**实测中改了一次阈值**：`quotes.toscrape.com/js/` 只有 2 个 script、没有框架骨架、没有 noscript，原来"脚本 ≥3"的门槛没触发。改成"任意脚本 + 正文极短"即触发。这会让"短静态页 + 一个统计脚本"也渲染一次——两种代价不对等：多渲染一次是一次页面加载且结果没变多就丢弃，漏判则是永久存一个空页。测试里把这个取舍写明了。

实测：`quotes.toscrape.com/js/` 正文 **78 → 1272 字符**，日志还提示"5/5 全需渲染，不如直接配 htmlunit"。

### 四种 extractor 全部真实站点实测

之前只有 RestClient 和 HtmlUnit 跑过真实站点，Playwright 和 Selenium 只有桩测试。补测后（`quotes.toscrape.com/js/`，一个真正靠 JS 渲染的页面）：

三种引擎作为 adaptive 回退目标也逐个实测：都正确检测到未渲染并成功渲染（4/4 页 100%）。

新增 `BrowserExtractorIT`（6 个用例，三引擎 × 直接渲染 / adaptive 回退）。**默认跳过**——Playwright 要下浏览器、Selenium 要本机装浏览器，构建机上失败与爬虫本身无关。开启方式：

```
mvn test -Dgreenfinger.browsers=true
```

### adaptive 设为默认 extractor

`default-extractor` 从 `restclient` 改为 `adaptive`。理由：另外两个选择都更常出错——纯 http 遇到自渲染站点会静默存下空页，固定浏览器引擎则在绝大多数根本不需要渲染的页面上付出一个数量级的代价。静态站点在 adaptive 下一个浏览器都不会启，所以开着不花钱。

**改默认立刻暴露了一个真问题**：浏览器引擎是 optional 依赖，starter 单独嵌入时不在 classpath 上，40 个集成测试全挂在 `No browser engine on the classpath`。改为**降级而非抛错**：没有浏览器就退回纯 http，并打一条明确的 warn 说明"会渲染的页面将被存成空壳，加 htmlunit/playwright/selenium 可启用渲染"。

**回退顺序也纠正了**：原来是 Selenium 优先，方向反了。HtmlUnit 才是唯一零安装的——引擎就在 jar 里；Playwright 要 `playwright install` 下几百 MB 浏览器，Selenium 要本机装 Chrome/Firefox。现在顺序是 `htmlunit → selenium → playwright`，`GF_ADAPTIVE_BROWSER` 默认也是 htmlunit。

CLI 实测（不指定 `--extractor`）：`quotes.toscrape.com/js/` 自动启动 htmlunit，4/4 页渲染，正文 1657 字符。

### 依赖关系纠正：cli 只依赖 core

原来是 `cli → starter → core`，但 starter 的定位是**面向 web**，CLI 不该穿过它拿服务、更不该被 servlet 依赖牵连。改成两个前端并列：

```
              ┌─ greenfinger-cli                （面向命令行）
core ─────────┤
              └─ greenfinger-spring-boot-starter（面向 web）
```

- 服务层（`CrawlerLauncher`、`CatalogAdminService`、`DeletionService`、`ReplayService`、`VersionPruner`、`EmbeddingWarmUp`、`GreenfingerConfiguration`）从 starter 搬进 core 的 `com.github.greenfinger.service` 包
- starter 只剩 `EnableGreenfingerServer` + `web/`（4 个类）
- 启用注解拆成两层：core 的 `@EnableGreenfingerCrawler`（引擎+服务，CLI 用）、starter 的 `@EnableGreenfingerServer`（前者 + REST，web 用）
- 对应的测试也按分工搬：服务层集成测试进 core，web 测试留 starter（各自带一份 `LocalSite` / `StubJsonServer`）

副作用：starter 覆盖率从 84.5% 升到 **92.4%**，因为它现在职责单一了。

### CLI 退出行为验证，修掉两个真 bug

系统验证了 `greenfinger-cli.sh` 跑完能否干净退出。**进程层面全部正常**——文件/ES/向量三路、三种浏览器引擎、本地模型、交互模式，退出码明确，无残留 java 进程，无残留 chromedriver / headless_shell。但退出码语义有两处不对，都是真 bug：

**1. 非必需输出层打开失败会掐死整轮爬取**
`CompositeOutputChannel.open()` 没做 `write()` 那样的"非必需层失败只 warn"处理。ES 连不上 → 整个命令失败、**一个文件都没写**，与设计文档明确矛盾（index/vector 失败应只 warn + 计数，事后 replay 补）。
修复：`open()` 逐个尝试，打不开的非必需层被丢弃并记入 failures，后续 `write`/`flush`/`close` 只走 `activeChannels`。warn 里直接给出补救命令。
实测：ES 不可达 → 退出码 0、文件正常写入 4 篇、warn 提示 `replay --catalog esdown2 --layers index`，照做后 4 篇成功补进 ES。

**2. 一页没爬到却报成功**
域名解析不了时退出码是 0。对脚本调用来说这是最糟的答案。
修复：CLI 在收尾时检查，**三个计数全为零**（saved / duplicated / existing）才算失败。条件收得很紧是有意的——merge 遇到未变更站点、update 没发现新页，saved 都是 0 但都是正常结果，它们的共同点是页面仍被"触达"过。
实测：坏域名 → 退出码 1 + `Nothing was reached: 1 url(s) seen...`；未变更站点的 merge → 退出码 0。
