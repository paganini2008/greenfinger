## 1. e2e 从 6 个到 15 个

`e2e/support.ts`：把两个账号和 `signIn` 抽出来共用。仍然走登录表单而不是直接塞 token——
表单本身就是被测对象，塞 token 的话服务端哪天不认这个 token 了测试还会一直绿。

**`e2e/search.spec.ts`（6 个）** —— 三种检索模式各打各的后端：

| 用例 | 断言的是什么 |
|---|---|
| words | `.gf-result-meta` 有 match 数和耗时，有高亮片段（向量库给不出高亮） |
| words 翻页 | 点 Next → page 2 且首条变了，点 Previous → 首条回来（游标翻页往返） |
| meaning | `similarity 0.xxx` 而不是命中数——向量检索答的是"最近的 n 条"，没有 total |
| pictures | 出图，且 `see it in place` 保留原始 imageUrl |
| pictures 翻页 | 第二页首图和第一页不同，说明 offset 下推到了向量库 |
| 切模式 | 切走之后上一个模式的结果块消失 |

**`e2e/delete-versions.spec.ts`（3 个）** —— 唯一不可撤销的操作前面的 dry run：

- keepLatest=0 + all → 计划表列出每个版本每一层，**然后什么都没删**：
  重新加载页面、再搜一次，数据还在。一个偷偷删掉的 dry run 在有人读完报告决定不删的
  那天之前，看起来和正常的一模一样
- keepLatest=99 → "Nothing to remove"，不出表
- support 角色**看不到** danger zone（是不渲染，不是禁用）

两个 spec 都写了前置条件：需要一个爬过且开了 index+vector 的 catalog（本地是 `books2`），
`GF_E2E_CATALOG` 可以换。没有的话第一条断言的失败信息会直说，而不是在空库上绿着过。

## 2. 图片检索：浏览器里一张图都出不来

`pictures` 那个用例第一次跑，`.gf-shot` 有，里面的 `<img>` 没有——全部走了
`isMissing` 分支。查下来是：

```
GET /v2/image?path=...   带 token   → 200 image/jpeg 12841 字节
GET /v2/image?path=...   不带 token → 401
```

`<img src>` 是浏览器直接发的请求，**auth interceptor 管不到它**，所以必然 401。
后端 9-01 验过这个端点，验的是 curl 带 token 那条路。

修法上有三个选择：把端点放公开、token 塞查询串、或者前端自己取字节。
选第三个——**不为了让一个标签能拉图就把所有归档图片放到登录之外**，token 也不该出现在
URL 和访问日志里。

- `ApiService.imageUrl(path)` → `imageBytes(path): Observable<Blob>`，`responseType: 'blob'`，
  照常过 interceptor
- 搜到图之后 `loadPictures(hits)` 逐张取，`URL.createObjectURL` 存进 `pictures` signal
- 新搜索、切模式、组件销毁时 `releasePictures()` 逐个 `revokeObjectURL`
- 模板从 `@else` 改成 `@else if (imageUrl(hit))`：**空 src 会触发 `(error)`，
  把一张还没到的好图标成 missing**，这是改的时候差点埋进去的坑

`api.service.spec.ts` 加了一个用例钉住 blob 请求的形状（29 个 vitest 全绿）。

## 4. Cluster 页（新）

`/cluster`，读 Spring actuator 的 `/actuator/spreader`。这一页存在的理由是：
**上面的每一个数字，别处都不会告诉你。**

- 入站缓冲满了是**静默丢弃**的（spreader 的设计如此——阻塞生产者会把整条派发链拖垮），
  所以 `dropped` 非零就是真实的业务损失，而且没有任何日志会提到它
- 一个看不到 leader 的节点是"活着、应答、什么也不做"，健康检查是 UP
- 成员数为 1 的节点会照常跑爬取，只是全在自己身上

页面把这三条做成告警条排在最前面，而不是埋在表格里。通道表是每种消息一行
（爬取 URL / 三条复制通道 / 集群自己的），带 sent / received / failed / dropped 和缓冲水位条。

**一个节点只答自己那一份**，页面顶上写明是哪个节点——把一个节点的数字当成集群的，
恰好会藏住那个已经不干活的节点。空通道表会显示"还没有流量"而不是一张空表，
因为空表读起来像集群坏了。

## 5. Monitor 页加"运行历史"，带图

每次爬取结束会写一份报告（后端第 9 节），这一节把它画出来：

- **柱状图**：每次运行一根柱，高度是保存的页数，点一根看详情
- **分段条**：派发的 URL 是整条，分成"已处理"和"剩余"两段——两个数字并排放着回答不了
  "比例是多少"，一眼能看出来的是条形
- **按节点分解**：每个节点贡献了多少页。单节点时这一段不显示（只有一行，什么也说明不了）；
  多节点时它是唯一能看出"有个节点整轮没干活"的地方

手画 SVG/CSS，没引图表库：一共几十根柱和两段条，任何一个库都比这整页大。

`Urls seen` 拆成了 `Urls dispatched` / `Urls handled` 两个计数——它们相等才叫爬完了。

### 修掉一个自己埋的坑

报告面板一开始不出现。原因：慢轮询（10 秒）从没看到过 `live=true`，
因为一页的爬取在两次轮询之间就跑完了，"从运行变为结束"的转换根本没发生过，
于是报告再也没被拉过。改成慢轮询时顺带刷新报告——顺便也能接住从命令行发起的爬取。

## 文件恢复（下午追加）

后端 replay 现在多了一层：文件也能恢复了（按数据库里的 `resource.url` 和
`resource_image.source_url` 重新去取）。前端相应地：

- Monitor 页的菜单加了 **Restore missing files from their urls**，调
  `replay(ref, ['file'])`。和 "Replay index and vectors" 分成两个入口而不是合成一个——
  它们的代价差着数量级：一个是从数据库重建，一个是重新发几百个 HTTP 请求。
- 删除确认里那句 **"Files that are deleted cannot be replayed back into the index"**
  已经不对了，改成："index 和 vector 可以从数据库 replay 回来；文件只能重新去站点取，
  而且得站点还在提供。"
- `api.service.spec.ts` 加了一条：`layers` 只有在显式选择时才会带 `file`。
  这条对应后端的 `parseExact`——`OutputType.parse` 会无条件加 FILE，照旧用它
  `replay --layers index` 会连带重新抓全站。


### e2e 跑在哪个后端上——排查时先看这个

今天在这里绕了很久：e2e 的 `baseURL` 是 `GF_E2E_URL ?? http://localhost:8088`，**直接打后端
的 jar，不经过 4200 的 dev server**（`proxy.conf.js` / `GF_API_PORT` 只影响 `npm start`，
对 Playwright 没有任何作用）。而 `search.spec.ts` 的前置条件是 `books2` 这个目录，它在
`deploy/data` 里，也就是 `greenfinger-api.sh` 起的那个独立节点上——**不在 run-local 的集群
节点上**（那些用 `data/node-N`，各自独立的库）。

所以：把 `GF_E2E_URL` 指向 50080 会让 10 个搜索用例全挂，不是前端坏了，是那个节点上没有
`books2`。正确的跑法是先 `./greenfinger-api.sh`（默认 8080），再
`GF_E2E_URL=http://localhost:8080 npx playwright test`。
