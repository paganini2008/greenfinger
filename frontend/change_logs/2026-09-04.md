2026-09-04 frontend
========================================

Four changes, three of them small. The backend day was a refactor of how a crawl decides it is
over, and two of its results reach the api the front end reads.


## The monitor draws two progress bars
------------------------------

A crawl ends on whichever of its two limits arrives first -- `maxFetchSize` or `fetchDuration` --
and the single bar could not say which. 60% of the pages and 60% of the time look identical and
mean quite different things about how much longer this will take. 1.x drew one per limit; so does
this now, labelled `pages` and `time`, stacked so they can be compared at a glance.

`CatalogSummary` gained `sizeProgress` and `timeProgress` for it. **`progress` is unchanged** --
still the nearer of the two -- so the hero's "Of the limit" stat and anything else reading it keeps
working.


## `interruptionReason` became `completionReason`, plus `interrupted`
------------------------------

`GET /v2/catalog/{ref}/summary`

| Field | Was | Now |
|---|---|---|
| `interruptionReason` | set only when a run was cut short | **gone** |
| `completionReason` | — | **new**: why the run ended, either way |
| `interrupted` | — | **new**: whether that was a completion or an intervention |

Why both: the crawl now records a reason whenever it ends, including when it ended normally
("reached maxFetchSize", "the site is exhausted: all 412 url(s) handled"). A reason being present
no longer means something went wrong, so the flag has to say which it was. It is also what decides
whether the version was published -- an intervention publishes nothing.

The monitor's notice reads from both: a warning icon and "was cut short ... nothing was published
to search" when `interrupted`, an info icon and "the last run finished: <reason>" otherwise. An
older `settings.json`, written before the field existed, still reads correctly -- the server maps a
lone `interruptionReason` to `interrupted: true`, which is what it meant.

The table printed the server's enum name (`VECTOR`) next to layer pills that are lower case

## The e2e cleans up its data, not only its definition
------------------------------

`main-flow.spec.ts` created a catalog, crawled it and deleted the definition -- and deleting a
definition is deliberately only that, so every run left another `e2e-*` directory under
`deploy/data`. It now empties the catalog on the Monitor page first, then deletes the definition.
Tolerant of an empty plan, since a crawl that saved nothing has nothing to remove.

Open since 2026-09-02, and it was also the reason the delete dialog needed clicking through by
hand -- which this now does on every e2e run.

## The container is Node now, not nginx
------------------------------

`deploy/web/server.js`, about a hundred and fifty lines, no dependencies -- not express, not
http-proxy. What the container has to do is serve a directory, fall back to `index.html`, and
forward `/v2` and `/actuator`; Node's own `http` module does all three, and a `package.json` here
would mean an npm install in the image, a lockfile to keep current, and a supply chain for a
hundred lines of code. `Dockerfile.web` is `node:22-alpine`, runs as `node` rather than root, and
`web/nginx.conf.template` is gone.

Forwarding is round robin over `GF_UPSTREAMS`, and a request that never reached a node is retried
against the next one. Only that: a request that was answered belongs to the node that answered it,
and sending a second copy of a crawl request somewhere else because the first was slow would start
the crawl twice.

**The port is 9700** -- the container's, and the dev server's, so "the front end is on 9700" is
true either way. `GF_WEB_PORT` still overrides it. (It was 50079.)


## `apiBaseUrl` is configuration, and the only one
------------------------------

`API_PREFIX` was the constant `'/v2'`. It now reads `window.__GF__.apiBaseUrl` from `public/env.js`,
loaded before the bundle, and appends `/v2`. Empty by default, which is right in both the ways the
app is normally served -- the dev server proxies `/v2`, and the api jar serves the page and the api
from one process -- and the container writes it from `GF_API_BASE_URL` in `.env` when the api is
somewhere it is not forwarding to.

Read at run time rather than baked in at build: the front end is its own container, and changing
an address should not mean rebuilding the app.

The `/v2` suffix stays fixed. It is the api's version, versioned with the product, and it has to
match `GF_API_PREFIX` on the backend.

**That is the whole of the front end's configuration.** `COUNTING_TYPES` and `EXTRACTORS` in
`api.models.ts` look like settings and are not: they mirror backend enums, a value that does not
match is a 400, and nothing is gained by letting anyone edit them.


## The delete panel asks which of two things you mean
------------------------------

It offered one operation with a layer picker, and the difference people actually care about was
not on the page at all. Two named choices now, side by side:

| | What goes | What is left |
|---|---|---|
| **Empty this catalog** | every version: rows, files, index, vectors | the catalog, defined and back at v0 |
| **Delete it entirely** | the same, and the catalog itself | nothing |

They are very nearly the same operation -- the only difference is whether the catalog row survives
-- which is why they are two labelled choices rather than a checkbox called "purge". "Empty this
catalog" and "delete it entirely" is how somebody thinks about it a moment before doing it.

Deleting entirely is offered only when nothing is being kept: removing the catalog from under three
versions that are staying is not a thing anybody means. Choosing it sends the version delete first
and the catalog delete second -- the other way round would leave the files and the index with
nothing that names them -- and then goes back to the catalogs page, because the page it was on no
longer has a subject.

**Emptying puts the version numbers back.** A catalog whose v0 to v2 have gone is a catalog that
has been defined and never crawled, so `index_version` returns to 0 and there is no search version.
Without that the next crawl wrote v3 into a catalog whose v0 to v2 exist nowhere -- a first crawl
reporting itself as the fourth. Removing *some* versions leaves the numbering alone, because the
rest are still there.

Two api fixes went with it: `deleteVersions` was still sending `before`, which the server dropped
on 2026-09-03, and it had no way to send `purge` at all.

**Not supported, and worth knowing:** emptying or deleting *several catalogs at once*. One catalog
at a time, any number of its versions.


## The two delete choices asked for the wrong thing
------------------------------

Both of them sent `keepLatest: 0`. The api reads an absent version and an absent keepLatest as
"the whole catalog", and `keepLatest: 0` as "every version, listed by name" -- and naming a version
that search is currently serving is refused, on purpose, because taking it out from under a live
search deserves to be said out loud. So both choices went down the path that guard protects, and
on any catalog that had ever finished a crawl -- which is any catalog worth emptying -- both came
back with "pass --force to remove it anyway". Neither choice has a force button, and neither
should: the operator has already named which of the two they want and confirmed it in a dialog.

The second half was `purge: this.keepLatest() === 0`, which sent purge for both choices. Purge is
the catalog row itself. It is the entire difference between "清空 catalog" and "彻底删掉", and it
was being decided by how many versions were kept rather than by which button was pressed -- so
"empty" would have deleted the catalog too, had the request ever got past the guard.

Both now go through one place, `deleteOptions`, which says what the three shapes are and why:
keeping some versions names them, keeping none names nothing at all, and purge goes only when the
operator chose to delete entirely.


## The dev server was proxying to a port nothing answers on
------------------------------

`proxy.conf.js` defaulted to **8080**. The server's default port has been **50080** for a while
now, and 8080 on this machine is nginx -- so `npm start` out of the box sent every api call to
nginx, which answered with its own 404. Not a 502, which would at least have said "nothing is
there": a 404 from a stranger looks like the api replying that the endpoint does not exist.

The default is 50080, which is where `run-local.sh` puts the first node. `GF_API_PORT=50081 npm
start` points it at the second one.

This is the kind of thing that only bites a new checkout. Anyone who had already exported
`GF_API_PORT` never saw it.

## `apiBaseUrl`, asked about often enough to write down
------------------------------

One file, `public/env.js`, one line, loaded by `index.html` before the bundle and copied verbatim
into the build -- so it is a runtime setting, and changing it does not mean rebuilding.

Three places to change it, depending on what you are doing:

| | Where |
|---|---|
| Developing | Leave it. Empty means same origin, and the dev server proxies `/v2` and `/actuator` to a node. Use `GF_API_PORT` to pick which node. |
| An already-built copy | Edit the line in `dist/greenfinger-ui/browser/env.js` or `deploy/docker/static/env.js`. No rebuild. |
| Deployed with docker | `GF_API_BASE_URL` in `deploy/.env`; `run-docker.sh` writes the file from it. |

Empty is right for both containers and the api jar, because in both the page and the api arrive on
the same origin. Only an api on a separate address -- its own domain, an nginx or Kong in front --
needs it set.

`/v2` is not in there on purpose: it pairs with `GF_API_PREFIX` on the backend, and the two have
to be changed together, so it is not a front-end setting.
